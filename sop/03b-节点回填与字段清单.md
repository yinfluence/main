## 节点层怎么补

### 总原则

不是为了让“关联概念 / 关联模型 / 关联人物 / 关联主题”显示出来才去补节点。

而是因为：

- 这个节点真的能跨节目复用
- 它不是只服务这一集
- 它值得作为独立入口存在

### 概念怎么抽

概念比模型更小，回答的是：

- 这里到底出现了什么现象？

判断标准：

- 是否能用一句话定义
- 是否可能在别的节目再次出现
- 是否比节目标题更稳定

例如：

- `价格发现延迟`
- `隐形债务`
- `公司身份迁移`
- `语言工具化`

### 模型怎么抽

模型比概念更高一层，回答的是：

- 这些现象背后反复出现的机制是什么？

模型应该比概念更少、更稳。

优先复用已有模型：

- `路径依赖`
- `委托代理问题`
- `反馈回路`

如果已有模型不够，再新增新的中层模型。

例如：

- `资产负债表维持`
- `风险转移链条`
- `制度适配`

### 人物怎么补

只有人物真的构成该期的重要角色时才补。

不要因为 transcript 里提了一次名字就强行建人。

适合补人物的情况：

- 人是这期判断的关键载体
- 这个人在多期节目中重复出现
- 用户点进去确实会想知道“他是谁、为什么重要”

### 主题怎么补

主题是跨多期的议题层，不是标签升级版。

一个主题应该回答：

- 这些节目为什么应该被放到一起看

例如：

- `房地产去杠杆与风险出清`
- `价格托底与账面维稳`
- `AI创业、资本主场与公司身份`
- `小国平衡与地缘生存`

## 各节点最小字段清单

新增或补全概念 / 模型 / 人物 / 主题 / 关键词节点时，每类至少要有以下字段；详细写法见各自类型规格（关键词见 `sop/01-关键词治理.md`）。

### 概念 `content/concepts/*.json`

每个概念都要能单独成立，最少要有：

- `name`
- `summary`
- `definition`
- `importance`
- `episodes`

### 思想模型 `content/models/*.json`

每个思想模型最少要有：

- `name`
- `summary`
- `definition`
- `application`
- `sourcePath`
- `episodes`

### 人物 `content/people/*.json`

人物不是简单标签，必须有最小介绍。注意：`content/people` 是源数据层，不再作为前台独立入口，站点会把人物并入关键词页。

- `summary`
- `description`
- `episodes`

要求：

- `summary` 先回答“这个人是谁”
- `description` 先补这个人的背景，再写“在这些节目里主要怎么被提及”
- 外国人物补 `englishName`
- 如果改过旧 slug，旧写法放进 `aliases`
- 不能只写标签式名字，必须有一句到一段可直接展示在网页上的简单背景介绍
- 不要让 `description` 一上来就是：
  - `在颖响力知识库里……`
  - `为什么重要……`
- 人物源数据的优先顺序是：
  1. 这个人是谁
  2. 他/她在这些节目里主要承接什么讨论线

### 主题 `content/themes/*.json`

主题用于把多个节目按议题聚合，最少要有：

- `summary`
- `description`
- `episodes`

### 关键词 `content/keywords/*.json`

关键词层用于承接品牌、人物、产品、公司、实体等更具体的检索入口，类似 GV 的公司层。人物对外统一从这里进入，不再保留独立人物页体系。

最少要有：

- `summary`
- `description`
- `aliases`
- `relatedKeywords`
- `episodes`

要求：

- `summary` 先说明这个关键词是什么类型的对象，例如人物、公司、品牌、产品、实体入口
- `description` 必须先写“它是什么 / 做什么”，再写“它为什么在颖响力知识库里重要”
- 如果这个关键词对应某个人物，优先复用 `content/people` 的信息，不要再手写一份相互冲突的人物介绍
- `relatedKeywords` 用来放：
  - 近义但不应并入 `aliases` 的相近词
  - 上位词 / 下位词
  - 同一议题簇里需要互相跳转的相关词

例如：

- 人物关键词：先写这个人是谁，再写其在专题里的位置
- 公司关键词：先写这家公司做什么，再写它在节目里代表的结构问题
