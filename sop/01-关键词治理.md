## 关键词分类与类型规格

关键词页的目标不是解释“为什么本站保留这个入口”，也不是套一句“在当前知识库语境里”。它更像一个小型 wiki 加节目索引：先把词本身讲清楚，再说明它在颖响力节目里怎样被使用，最后给读者一点可继续展开的关联线索。

关键词必须先判断类型，再按类型写。`kind` 必须使用固定英文枚举，中文只作为展示名：

- `person`（人物）：先写硬事实和基础身份，再写节目怎样使用这个人物，最后写个人风格、做事方式和延展关联。不能只写抽象风格，也不能只写传记流水账。例如特朗普必须写明“美国第45任与第47任美国总统”这类基础事实。
- `geography`（地缘/地点）：重点写它作为国家、地区、港口、海峡、航线或地缘节点，怎样影响规则、成本、通道和安全预期。
- `organization`（公司/机构/平台）：重点写组织角色、商业模式、监管位置、权力结构和外部影响；不要只写公司百科。
- `product`（产品/品牌/技术对象）：重点写它在节目里暴露出的技术路线、运营风险、用户关系、产业链位置或公共后果。
- `event`（事件/战事/风波）：重点写事件的成因、冲突结构、后果和节目拿它说明的长期问题；不要只复述新闻。
- `mechanism`（机制词）：重点写这个词概括了什么运作机制、因果链或制度动作。机制词强调“它怎样运作”，不是抽象解释。
- `concept`（概念词）：重点写这个词的直观定义、节目语境和与正式概念页的关系。概念词强调“它是什么意思、为什么这样理解”，不是把它写成机制链。
- `theme`（主题词）：重点写跨节目问题线和阅读入口。主题词强调“哪些节目被归到同一条线”，不是单个案例、单个概念或百科条目。
- `asset`（金融资产/大宗商品）：重点写它作为资产、商品、信用参照物或交易对象，怎样连接价格、平台、货币体系、风险情绪和现实交易结构。黄金、白银、比特币这类词优先考虑此类，而不是塞进常规词。
- `general`（常规词）：如果不属于上述类型，就按普通关键词处理，写清它在节目语境里的具体含义、主要场景和相邻节点。

分类必须人工确认。允许脚本先推断类型，但最终写入内容前必须由整理者确认；必要时在关键词 JSON 里加 `kind` 字段固定分类，避免靠字面误判。例如“英文知识库存管理”里如果站内词条是“库存管理”，不能因为出现“知识库”就把“知识库”自动识别成关键词。

关键词治理的总原则：

- 所有关键词只有一套统一标准：先判断它实际承载的对象类型，再按该类型的固定字段写厚，最后按同一套审核清单验收。不能因为某个词来自节目标签、人物抽取、手写关键词页或批量定义文件，就使用不同质量标准。
- 数据文件只是承载位置，不是内容标准。`content/keywords`、`content/people`、`scripts/keyword-definitions.json` 和 `scripts/keyword-definitions.d/*.json` 都可能影响关键词页面；整理时必须按最终网页里的关键词页面质量来验收，而不是只看某一个目录是否改过。
- 旧关键词、新节目新增关键词、手动补充关键词都走同一流程：抽取候选词 -> 判断是否值得保留 -> 判定 `kind` -> 写入该类型字段 -> 核对节目关联 -> 核对必要外部事实 -> build -> 审计 -> 页面抽查。
- 新节目进入知识库时，新增关键词不能先用“当前知识库语境里”“值得保留”“后续维护”这类占位话术糊过去。即使先做初稿，也必须至少写清“它是什么 / 节目怎么用它 / 读者还能沿什么线继续看”。
- **新节目入库的关键词强制清单（违反即不算完成）**：每一期节目入库时，本期 `tags` 字段里的每一个词都必须有对应处理动作，二选一不能跳过——(a) 词已存在：核对该关键词的 `episodes` 数组是否包含本期，缺失就补本期 `id + note`，并判断这期内容是否补充了新的 `signalNotes / programAssociations`；(b) 词不存在：必须在 `content/keywords/`（或 `scripts/keyword-definitions.d/` 分片）新建词条，写清 `kind / summary / description / signalNotes / episodes` 等该 kind 的必填字段，不允许只留 build 自动生成的 stub（如“XX是本期节目里单独展开的一项对象或说法”这种占位句）。新节目算完成的前提是：本期 tags 数量 = 已写过或本轮已写的 keyword 词条数。验收方式：`grep` 本期 id 在 `content/keywords/` 命中数 ≥ `tags.length`，缺一不收。
- 关键词正文和结构字段不能留下 `待补充`、`暂无`、`后续补充` 等占位内容。写不出有效内容时，先判断这个栏目是否必要：必要就补成有信息量的内容，不必要就删除该字段或让前台隐藏，不允许把空栏目交给用户。
- 关键词正文不能出现内部审稿口吻。`站内保留这个词`、`节目保留这个词`、`这个词条`、`本词条`、`候选入口`、`厚词条`、`未在本轮复核` 这类话会把读者拉回后台维护视角，必须改成自然的事实说明、节目用法或风险边界。
- 批量重写的目标不是把每个词写成一样长，而是让每个词都符合自己的类型标准。人物像小型 wiki；地缘节点要讲地图、通道和规则；机构要讲组织位置和暴露的问题；机制/概念要讲清定义和运作；事件要讲时间线、参与方和后果；资产要讲价格、信用、平台和风险承接。
- 速度可以通过多 agent 并行提高，但质量不能靠降低标准换取。允许先出初稿，但初稿也必须能过结构门槛；事实查不到时要标注“待核”或改成节目归因表达，不能编成确定事实。

主类型由“页面标题实际承载的对象”决定，不由节目临时讨论角度决定：

- 如果页面标题是一个人，就按 `person` 写，即使节目主要借他讨论国家战略、公司治理或意识形态。
- 如果页面标题是一家公司或机构，就按 `organization` 写，即使节目主要借它讨论债务风波、接班危机或监管事件。
- 如果页面标题是一个稳定事件名，例如某场战争、某次风波、某项政策事件，才按 `event` 写。
- 如果一个组织反复作为事件被讨论，先把组织页写厚；只有当事件本身有稳定名称、独立节目关联和独立延展价值时，才另建事件页。例如“万科”仍是机构页，“万科债务危机”只有在后续需要独立承接时才拆成事件页。
- 如果一个词同时像概念又像资产、产品或地缘节点，优先按节目主要使用方式判定。黄金、白银、比特币、石油美元这类词，只要节目主要讨论价格、信用、结算、平台风险或资产避险，就按 `asset` 写。
- `general` 是兜底类型，不是低质量类型。只有确实无法归入前面类型，但又能写清基础含义、节目关联和延展逻辑时，才保留为 `general`。

关键词扩展字段的统一结构：

- `kind`：固定英文枚举，只能用 `person`、`geography`、`organization`、`product`、`event`、`mechanism`、`concept`、`theme`、`asset`、`general`。
- 关键词首页不直接把十种 `kind` 平铺给读者。顶层入口固定收成 5 个更易读的方向：`人物机构`、`地区事件`、`产业资产`、`概念机制`、`长期主题`。十种 `kind` 仍然是数据和详情页类型标签的标准，但在首页降到第二层。
- 十种类型的前台展示名固定为：`人物`、`地理位置`、`公司机构`、`产品技术`、`资产商品`、`事件`、`机制`、`概念`、`主题`、`通用类`。命名要短、同一节奏，不加“关键词”后缀；详情页上的类型标签必须能跳回关键词首页并展开对应类型。类型标签跳转时，需要自动展开所在顶层入口和对应类型。
- 关键词首页禁止使用“展开更多”兜底。每一层可见分组如果超过 8 个条目，必须继续分化为更小的语义组，直到叶子组不超过 8 个条目。禁止用“高频 / 中频 / 低频”“1-8 / 9-16”“补充 1 / 补充 2”这类统计切片伪装分类；分组名必须说明这些词为什么在同一条问题线里。顶层、类型层、细分层和继续分化后的叶子层都要接入右侧轮盘；用户展开到哪一层，轮盘就必须能显示并跳转到那一层。
- `general` 前台显示为 `通用类`，只能收纳确实难以归入其他九类、但仍有解释价值的词。不能把没有想清楚的词随手丢进通用类；审核时优先检查通用类是否混入明显的资产、机制、产品、事件或机构词。
- `asOf`：事实核对日期，格式 `YYYY-MM-DD`。涉及现代职务、现任身份、上市状态、战争进展、公司状态、产品状态、价格/排名/市场数据时必须写。稳定历史事实可以不写，但批量重写时建议统一保留。
- `sources`：事实来源数组，每项格式为 `{ "title": "...", "url": "...", "note": "核对了什么" }`。只放事实核对来源，不放节目观点来源；`note` 必须写明核对的是哪类事实，例如身份、任期、股东、人口、吞吐量、财务状态、事件时间线。节目原创机制词如果没有外部事实需要核对，可以写 `sources: []` 或省略 `sources`，但正文必须明确“在节目语境里/节目把它理解为”，不能伪装成外部事实。
- `episodes`：顶层 `episodes` 使用现有内容文件格式，必须是对象数组：`[{ "id": "EPxxx", "note": "..." }]`。不要把顶层 `episodes` 改成纯字符串数组。
- `programAssociations`：数组，每项必须是 `{ "title": "...", "episodes": ["EPxxx"], "note": "..." }`。`title` 是问题线，不是长句；`episodes` 只放真实相关节目；`note` 必须先交代这些节目各自讲了该词条的什么具体材料，再归纳节目把这个词放进哪条机制、冲突或现实问题。不能只在开头列 `EPxxx、EPxxx`，后面直接跳到抽象判断。
- `signalNotes`：内部字段名，前台非人物关键词显示为“常见场景”。人物页不显示这个字段；人物的厚度必须由基础介绍、节目关联、个人风格、做事方式和延展阅读承担。非人物关键词默认都要写 `signalNotes`，每条都要写出“信息/场景 + 判断含义”，不能只写关键词堆。例如不要只写“马六甲海峡、保险、护航”，要写清这些信息连在一起时，节目是在讨论谁定义风险价格。注意这不是固定句式，不能每条都写成“当 A 与 B 同时出现时”。同一词条里的常见场景要像自然编辑写作，可以交替使用“看到……时”“它常在……场景里出现”“这类讨论通常指向……”“读者需要留意的是……”。只有极少数词确实没有相关信息场景时，才允许省略，并在审稿记录里说明原因。
- `extensionNotes`：数组，每项必须是 `{ "title": "...", "note": "..." }`。不再接受纯字符串或一句带冒号的自然语言。`title` 是可继续阅读的线索名，`note` 必须说明为什么延展到这个节点，不能只列节点名。
- 类型专属字段例如 `impactNotes`、`exposureNotes`、`consequenceNotes`、`conflictNotes`、`aftermathNotes` 只在确实能写出有价值内容时保留。不能为了凑栏目写空话，也不能让页面显示“待补充”。
- `summary`：一句话，身份/对象事实 + 节目主要用法。
- `description`：小型 wiki 基础事实 + 节目语境总定位。事实和节目判断要分开写。

节目关联落库规则：

- `programAssociations[].episodes` 里出现的节目，必须也能在词条 `episodes` 或由构建脚本推断出的相关节目里找到。试写阶段可以提出“候选节目”，但生产写入时必须同步补到 `episodes`，否则页面会出现正文提到某期、相关节目区却没有该期的断裂。
- 如果某期只是类比参照，不应该进入相关节目列表，就不要放进 `programAssociations[].episodes`，在 `note` 里用自然语言说明“可对照某类节目”即可。
- 同一个节目可以出现在多个问题线里，但不要为了凑数重复。优先按“机制/冲突/现实问题”分组，而不是按时间顺序分组。
- `programAssociations` 每项建议 80-180 中文字。低于 40 字通常写不清机制，高于 240 字通常应该拆成两组。
- 每个 `programAssociations[].note` 必须包含两层：第一层是具体节目内容，例如“EP107 用灰色石油网络说明……，EP136 用影子舰队说明……”；第二层才是归纳，例如“合起来看，节目把特朗普放进能源金融风险定价问题”。如果一组里有多期节目，却看不出每期贡献，说明分组太粗或内容太空。
- 试写草稿里可以暂用 `programAssociations[].episodes` 的字符串数组；真正落库时，必须把这些节目同步到顶层 `episodes` 对象数组，并为每个 `episodes[].note` 写一句“这期怎样使用该关键词”的说明。
- 构建脚本会自动把 `programAssociations[].episodes` 补入顶层 `episodes`，审计脚本也会检查缺失同步；但 agent 写稿时仍要主动写清每期节目贡献，不能把同步责任当成省略节目说明的借口。
- 不能为了让页面显示更多节目，把弱相关、只类比、只顺带提到的节目塞进 `programAssociations[].episodes`。弱相关只能写进自然语言延展，不进入相关节目区。
- 单期强关联允许只写 1 个高质量 `programAssociations` 分组，不要为了凑 2 组把弱相关节目塞进去。合格条件是：这一组必须写清该期节目具体材料、人物/词条在其中承担的角色、以及它连接到的机制或现实问题。

字段分工：

- `description` 回答“这个词在外部世界基本是什么 + 站内大致怎么使用”。
- `basicIntro` 只用于人物，回答“这个人是谁”，不写节目分析。
- `programRole` 只用于人物，回答“节目为什么使用这个人”，不重复基础履历。
- 各类 `*Role` / `*Notes` 字段回答“它在现实系统里起什么作用”。
- `programAssociations` 回答“哪些节目讲了它的哪些具体内容，以及这些内容合起来说明什么问题”。
- `signalNotes` 回答“这个词常和哪些信息、场景、相邻节点一起出现，以及这些关联说明什么”。它是自然语言知识关联，不是公式化提示；连续多条用同一个句式开头不合格。
- `extensionNotes` 回答“读者下一步可以沿哪些知识线继续看”。

人物页去重规则：

- 页头 `summary` 只写一句定位，不展开。
- `description` 只承担页头下的简短介绍，最多 1 段；不要和 `basicIntro`、`programRole` 复述同一套判断。
- `basicIntro` 只写硬身份事实：是谁、做什么、关键职务/身份、必要时间点。不写“节目为什么用他”。
- `programRole` 才写节目为什么使用这个人，且只写一次总定位；具体节目内容放进 `programAssociations`。
- `programAssociations` 不再重复人物身份，只写各期节目具体用法和问题线。
- 同一关键词、同一判断不要在 `summary / description / basicIntro / programRole / programAssociations` 里重复三次。读页面时应像层层展开，而不是同一句换说法。

事实与观点归因：

- 外部事实用稳定陈述句，并尽量配 `asOf` 和 `sources`。正文不要写“截至某日核对”“截至本次核对”“页面整理时”这类时效口吻；核对日期放在 `asOf` 或 `sources[].note` 里。
- 节目判断必须用归因措辞，例如“节目把它理解为”“节目认为”“在节目语境里”“节目借它讨论”。不要把节目判断写成外部事实。
- 不确定的现代状态不要写死成“现任”。优先写稳定历史事实、官方资料列明的身份，或改成节目归因表达；不要把核对日期塞进正文。
- 高风险或易变事实包括：总统/首相/部长/CEO/董事长、死亡/逝世、封禁/解封、离任/复任、股权收购、公司上市/破产/重整状态、组织退出、战争进展、监管处罚、产品召回、价格与排名。写入前必须核对。
- 外部来源里的解释性说法，例如“黄金是避险资产”“新加坡是金融中心”，可以作为市场惯例或事实背景写入；节目进一步提出的结构判断，必须另行归因给节目。
- 如果一个段落同时包含事实和节目观点，必须拆句写清楚：先写稳定事实，再写节目语境里怎样使用这个事实。

人物关键词页固定回答五件事：

- 基础介绍：真实身份、关键职务、时代位置和最少必要背景。人物事实不能省略。
- 节目关联：按节目问题线分组，不机械堆期数；每组都说明节目把这个人放进了哪条机制或现实冲突里。
- 个人风格：写稳定的表达方式、权力风格、商业/政治风格或决策偏好，避免简单褒贬。
- 做事方式：写这个人物如何行动、如何组织资源、如何改变成本、规则、关系或预期。
- 延展阅读：给出人物背后的国家、行业、地缘、制度、产品或事件线索；不要使用“相关节点”这种空泛栏目名。

非人物关键词页默认回答四件事：

- 基础介绍/对象说明/事件说明/概念说明/机制说明：按类型讲清这个词本身。
- 节目关联：说明它在哪些节目问题线里出现，以及节目拿它解释什么。
- 常见场景：写这个词通常出现在哪些案例、相邻词、现实场景或判断里，以及这些关联说明什么。
- 延展阅读：给出可继续阅读的相邻关键词、概念、模型或主题，但必须说明关联逻辑。

关键词页不使用“为什么重要”“使用边界”“相关节点”作为一级栏目。它们太容易变成模板空话；如果确实需要表达价值、限制或连接关系，必须自然写进上面四类内容里。

关键词页不写“进一步追问”。概念、模型、主题页也不再展示“进一步追问”。如果需要引导读者继续看，放在延展阅读、相关节目和正文自然链接里。

#### 关键词类型内容规格

所有关键词都要满足同一个目标：小型 wiki 事实解释 + 颖响力节目关联 + 站内延展。不同类型的写法不同，不能把下面栏目机械复制成同一句式。

类型判定优先级：

- 人物优先于机构。比如企业创始人、政治人物、学者、创作者，先按人物写；机构另做机构页。
- 事件优先于普通概念。只要词条指向具体历史节点、风波、战争、事故或政策事件，先按事件写。
- 地点如果承担通道、边界、安全、转运、资源或小国生存作用，按地缘/地点写，而不是普通地名。
- 公司产品混合时拆开：公司页写组织和权力位置，产品页写技术路线、用户后果和产业位置。
- 机制词和概念词要分开判断。能写出“输入、过程、结果、谁承担成本”的，优先按 `mechanism`；主要是在解释一个名词、说法、判断框架或观念边界的，按 `concept`。
- 主题词只有在它能把多期节目组织成一条稳定问题线时才使用 `theme`。单期出现、只像标签的词，不要为了显得高级写成主题。
- 金融资产/大宗商品优先于常规词。黄金、白银、比特币、石油美元这类词如果节目主要讨论价格、信用、结算、平台风险或资产避险，按 `asset` 写。
- 行业/资产系统词暂不新增独立类型，先归入 `general`，但必须按行业入口写厚。例如房地产不是普通词，要写清它同时承接资产、财政、家庭负债表、地方政府和金融系统；不能因为归入 `general` 就降低质量。
- 常规词是兜底，不是低质量词条收纳箱。若讲不出 wiki 基础、节目关联和延展逻辑，应合并到上位关键词。

##### 人物

推荐字段：`summary`、`description`、`basicIntro`、`programRole`、`programAssociations`、`styleNotes`、`methodNotes`、`extensionNotes`。人物页不要新增 `signalNotes`；历史遗留字段可以后续清理，但不显示、不审稿、不作为合格内容的一部分。

- `summary`：一句话同时交代基础身份和节目里的主要观察角度。
- `basicIntro`：写清真实身份、关键职务、任期/时代位置和最少必要背景。现代政治人物、企业家、学者、艺术家、内容创作者、主播、教育家、音乐人、作家等都必须有事实锚点。
- `programRole`：概括节目为什么反复使用这个人，是政策行动者、商业方法样本、时代情绪样本、制度位置，还是某条议题线的代表。
- `programAssociations`：按问题线分组，每组写 2-5 期节目或一个清晰节目切口，必须先写各期节目借这个人讲了什么，再说明节目把这个人放进哪条机制里。人物页尤其不能只写“EPxxx、EPxxx 把他放进某问题线”，要让读者知道每期节目里这个人承担了什么角色。
- `styleNotes`：写表达风格、权力风格、商业风格、组织风格或认知风格，不写简单褒贬。
- `methodNotes`：写这个人怎样行动，怎样调动资源、改变成本、制造压力、组织叙事或影响制度。
- `extensionNotes`：写人物背后的国家、公司、行业、制度、地缘、事件或概念线索。

边界：不是传记页，不写私生活八卦，不做道德判词，不把节目观点当事实；但关键身份事实不能省。

最低合格标准：`summary` 必须同时有身份和节目角色；五个展示栏目都完整；至少 2 组节目关联，或 1 组非常清楚的问题线；至少 3 条个人风格；至少 3 条做事方式；至少 3 条延展阅读；关键身份事实人工核对。

人物词条样例基准：`content/keywords/trump.json` 是当前人物关键词 v1 合格样例。后续人物批量重写要参照它的结构，但不能复制它的句式。尤其要保留三点：第一，基础介绍先把“他是谁”讲清；第二，节目关联要写各期节目具体借这个人讲了什么，再归纳问题线；第三，个人风格、做事方式和延展阅读要足够厚，不能靠额外“关联信息”栏目补空。

##### 地缘/地点

推荐字段：`summary`、`description`、`nodeRole`、`programAssociations`、`impactNotes`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明它是什么地缘对象，以及节目主要从哪条问题线使用它。
- `description`：交代基础位置、政治/经济身份、通道属性或边界属性。
- `nodeRole`：说明它是咽喉、缓冲区、港口、航线、国家样本、制度边界，还是资源/安全节点。
- `programAssociations`：写节目如何把它放进海峡、航运、资源、联盟、小国生存、边界规则或大国竞争里。
- `impactNotes`：写它影响谁的通行成本、风险定价、安全预期、贸易路线或制度选择。
- `signalNotes`：写它常出现在什么信息场景里，例如护航、保险、转运、港口、边界、能源通道，以及这些关联说明什么。前台标题显示为“常见场景”。
- `extensionNotes`：连接相邻国家、海峡、航线、地区冲突、公司和模型。

边界：不是旅游百科，不写完整国别史，不把地名当背景装饰；必须说明它为什么是现实结构中的节点。

最低合格标准：写清“位置 + 规则/通道作用 + 节目中的现实问题”；延展至少 3 个相邻节点，并说明关联逻辑。

##### 公司/机构/平台

推荐字段：`summary`、`description`、`positionNotes`、`programAssociations`、`exposureNotes`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明它是什么组织，以及节目主要借它讨论什么结构问题。
- `description`：写基础组织身份、业务范围、权力位置或监管位置。
- `positionNotes`：说明它在产业链、财政链、流量链、监管链或公共服务链中的位置。
- `programAssociations`：写节目如何把它作为案例，例如企业扩张、地方财政、平台治理、组织失灵、公共后果。
- `exposureNotes`：写它暴露的商业模式、制度激励、监管缝隙、风险转移或组织能力问题。
- `signalNotes`：写读者看到哪些财务、监管、舆论、治理或组织动作时，应联想到这个机构代表的结构问题。
- `extensionNotes`：连接人物、行业、政策、产品、概念和相关节目线。

边界：不是工商资料库，不列无关财报，不写品牌宣传；必须写出它在节目里承担的结构角色。

最低合格标准：`summary` 说明组织身份和节目角色；正文至少包含业务/权力位置、节目案例作用、外部影响；至少 2 条常见场景；延展不少于 3 条。

##### 产品/品牌/技术对象

推荐字段：`summary`、`description`、`objectRole`、`programAssociations`、`consequenceNotes`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明它是什么对象，以及节目从技术、产业、用户还是治理角度讨论它。
- `description`：写基本功能、技术路线、产品类型或使用场景。
- `objectRole`：说明它在现实系统中改变了什么，例如成本、体验、安全、劳动、供应链、数据或控制权。
- `programAssociations`：写节目如何借它讨论行业竞争、用户风险、技术路线、资本叙事或监管问题。
- `consequenceNotes`：写规模化后的后果，尤其是谁得到便利、谁承担风险、谁获得控制权。
- `signalNotes`：写这个产品/技术对象常和哪些使用场景、舆论叙事、事故、平台动作或产业变化连在一起，以及这些关联说明什么。
- `extensionNotes`：连接公司、人物、产业链、政策、事故、概念和模型。

边界：不是参数评测，不写购买建议，不罗列配置；必须从产品进入现实系统后的影响来写。

最低合格标准：至少有对象定义、使用/产业场景、节目中的风险或结构问题、常见场景、可延展的公司/技术/事件线。

##### 事件/战事/风波

推荐字段：`summary`、`description`、`conflictNotes`、`programAssociations`、`aftermathNotes`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明事件是什么，以及节目主要拿它观察什么问题。
- `description`：交代最少必要事实：时间范围、地点、参与方、事件性质。
- `conflictNotes`：写成因、利益冲突、制度背景或行动者选择，不只复述经过。
- `programAssociations`：写节目如何把事件放进更长的问题线，例如战争体制、财政风险、平台治理、社会情绪。
- `aftermathNotes`：写后果和余波，包括规则变化、风险暴露、心理冲击或制度反馈。
- `signalNotes`：写事件再次被提起时通常伴随哪些政策、价格、舆论、军事、平台或制度信息，以及这些关联代表什么后续判断。
- `extensionNotes`：连接相关人物、国家、机构、机制、主题和后续节目。

边界：不是新闻时间线，不追求报道大全，不替代事实调查；必须写清节目为什么用它作为切口。

最低合格标准：基本事实完整；至少写出成因、冲突、后果三件事；至少 2 条常见场景；节目关联必须超过复述新闻。

##### 机制词

推荐字段：`summary`、`description`、`mechanismNotes`、`programAssociations`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明这个词概括了什么现象或机制。
- `description`：用普通读者能懂的话定义，不用内部黑话。
- `mechanismNotes`：说明它怎样运作：输入是什么，过程是什么，结果影响谁。
- `programAssociations`：写节目在哪些案例里用它解释问题。
- `signalNotes`：写这个机制常出现在哪些现象、词组或案例里，以及这些关联为什么说明机制正在运作。
- `extensionNotes`：连接正式概念页、思想模型、主题页和典型节目。

边界：如果已经有正式概念或模型页，关键词页不要重复长篇理论；关键词页负责直观解释和导流。

最低合格标准：至少有直观定义、1 条机制链、1 个节目场景、2 个以上可跳转的概念/模型/主题或典型案例。

##### 概念词

推荐字段：`summary`、`description`、`conceptNotes`、`programAssociations`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明这个概念指什么，以及节目主要用它解释哪类问题。
- `description`：先用普通读者能懂的话讲清概念，再说明它在节目里的使用方式。不要写成“本站为什么保留它”。
- `conceptNotes`：写概念的关键层次、常见误解、与相邻概念的区别。重点是帮助读者理解词义和判断边界。
- `programAssociations`：写节目在哪些案例里用这个概念解释现实，不只说“某期提到了这个词”。
- `signalNotes`：写读者在什么语境里会遇到这个概念，以及这些语境提示他该怎样理解。
- `extensionNotes`：连接正式概念页、模型页、主题页、人物或典型节目。

边界：概念词不是长理论论文，也不是机制词的替代品。若正文主要在讲某个系统如何运作，就改成 `mechanism`；若正文主要在组织多期节目阅读，就改成 `theme`。

最低合格标准：概念定义清楚；至少说明 1 个常见误解或相邻概念区别；至少有 1 个节目场景和 2 条延展阅读。

##### 主题词

推荐字段：`summary`、`description`、`themeNotes`、`programAssociations`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明这个主题线覆盖什么问题，以及节目为什么把它作为跨期入口。
- `description`：写清这条主题线的范围、主要冲突和阅读价值。不要写成“后续可以继续累积”这种维护说明。
- `themeNotes`：写这条主题线下反复出现的观察维度，例如行动者、利益冲突、制度位置、风险转移、叙事变化。
- `programAssociations`：按问题线分组说明哪些节目共同构成这个主题，每组都要写各期节目贡献。
- `signalNotes`：写读者看到哪些案例、人物、机构或事件组合时，应把它们归到这条主题线下。
- `extensionNotes`：连接更具体的概念、模型、人物、事件、公司和典型节目。

边界：主题词不是普通标签。只有当它能承接多期节目、能解释一组反复出现的问题，才使用 `theme`。如果只是一个单点对象，改成人物、组织、事件、机制或常规词。

最低合格标准：至少覆盖 2 期节目或 1 条极强的长期问题线；必须写清归线依据；延展阅读不能只列节点，要说明为什么这些节点属于同一主题。

##### 金融资产/大宗商品

推荐字段：`summary`、`description`、`assetRole`、`programAssociations`、`riskNotes`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明它是什么资产/商品，以及节目从价格、信用、交易结构还是货币体系角度讨论它。
- `description`：写基础事实，例如资产属性、主要用途、交易形态、价格影响因素和普通人接触方式。
- `assetRole`：说明它在现实系统里承担什么角色，例如避险资产、结算工具、信用参照物、投机对象、平台交易品或大宗商品。
- `programAssociations`：写节目如何借它讨论散户风险、美元体系、制裁结算、平台信用、资源通道或价格叙事。
- `riskNotes`：写谁在什么环节承担风险，例如平台、托管、杠杆、流动性、点差、回收、监管、地缘或结算风险。
- `signalNotes`：写这个资产/商品常和哪些市场现象、交易条件或叙事连在一起，必须包含“场景 + 判断含义”。
- `extensionNotes`：连接货币体系、平台风险、制裁、能源、大宗商品、国家储备和相关节目线。

边界：不是投资建议，不预测涨跌，不写买卖点；必须区分资产事实、节目判断和普通人的交易条件。

最低合格标准：至少有资产定义、现实交易形态、节目问题线、风险承接方和延展逻辑。

##### 常规词

推荐字段：`summary`、`description`、`programAssociations`、`signalNotes`、`extensionNotes`。

- `summary`：一句话说明这个词在站内主要指什么。
- `description`：把字面含义和节目语境区分开。
- `programAssociations`：写它在哪些节目材料里成为关键词。
- `signalNotes`：写常见搭配、相邻说法、典型场景或读者容易误解的地方。
- `extensionNotes`：连接更具体的人物、公司、地点、事件、概念或模型。

边界：常规词不是低质量词的收纳箱。如果讲不出节目关联和延展逻辑，就不应该强行扩成厚词条。

最低合格标准：至少有具体含义、节目场景、相邻节点；如果三项都写不出来，应合并到上位关键词而不是单独保留。

关键词内容审核底线：

- 不能只出现“高频出现、重要入口、承接讨论、帮助理解、当前知识库语境”这类空泛表达。
- 每个词条至少要有一个“基础事实”或“对象定义”，一个“节目关联”，一个“延展阅读”方向。
- 人物词条必须人工核对关键身份事实；涉及总统、首相、CEO、创始人等现代职务时，不能只靠旧记忆。
- 节目关联必须回答“哪期节目讲了它的什么具体内容，以及这些内容被放进哪条机制、冲突或现实问题里”，不能只写“EPxxx 提到了它”，也不能只列 EP 后直接给抽象结论。
- 延展阅读必须说明关联逻辑，不能只堆相邻词列表。
- `signalNotes` 必须能让读者看到信息之间的关联，不允许写成“相关关键词：A、B、C”，也不允许整组都用“当 A 与 B 同时出现时”这类重复模板。
- 同一批词条不能出现明显复制粘贴的句式骨架。允许字段结构一致，不允许内容逻辑一致、只替换名词。
- 批量重写时先按类型分批，每批完成后抽查 10%，并至少检查：旧模板残留、内容重复、事实缺失、节目关联空泛、常见场景空泛、延展无逻辑。

SOP 修改权限：

- SOP 只能由主整理者统一修改，不能让多个 agent 并行直接编辑 SOP。
- agent 可以在最终报告里列出“SOP 缺口 / 歧义 / 建议”，但不得自行改 `SOP-知识库整理.md`。
- 主整理者审完 agent 输出后，先归并相互冲突的建议，再一次性写入 SOP，保证同一时间只有一套标准。
- 如果 SOP 变化会影响正在运行的 agent，主整理者要在 agent 完成后按新标准审查；必要时退回重写，而不是让运行中的 agent 临时改 SOP。
- 每次 SOP 变化都要用样例或审计规则验证，不能只写原则不落到字段、页面展示或审稿清单。

关键词单条审稿清单：

- 类型是否正确，是否需要拆页或合并到上位关键词？
- `summary` 是否同时说明“它是什么”和“节目怎么用它”？
- `description` 是否有小型 wiki 的基础事实，而不是站内空话？
- 事实与节目观点是否分开？现代事实是否有 `asOf` 和 `sources`？
- 顶层 `episodes` 是否是对象数组，且覆盖 `programAssociations[].episodes`？
- `programAssociations` 是否按问题线分组？是否先写各节目具体讲了什么，再说明机制/冲突/现实问题？
- `signalNotes` 是否写出了“信息/场景 + 判断含义”，而不是关键词堆？
- `extensionNotes` 是否每项都有 `title` 和 `note`，且说明为什么可以继续读？
- 是否出现禁用栏目名：“为什么重要”“使用边界”“相关节点”“进一步追问”？
- 是否能让不了解该词的读者获得基础理解，同时看懂它和颖响力节目的联系？

## 关键词整理规则

关键词层的目标不是“把字幕里所有名词都做成平级入口”，而是优先形成稳定、好用的专题入口。

### 1. 优先保留上位专题，不滥开平级同义入口

- 优先保留真正能承接节目群的专题词，例如：
  - `娃哈哈`
  - `新能源汽车`
  - `西贝`
- 不要把明显属于同一簇的近义词、口语词、下位表达全部做成平级专题。

例如：

- `新能源 / 新能源汽车 / 电车`
  应优先收束到 `新能源汽车`
- `宗馥莉 / 宗庆后 / 娃哈哈`
  如果当前讨论主线是娃哈哈家族与公司问题，应优先收束到 `娃哈哈`
- `杂粮汽车 / 小米汽车`
  应收束到正式入口 `小米汽车`

### 2. 别名和口语词放到 `aliases`

- 如果一个词只是别称、口语、戏称、缩写，不要再单独做一个平级关键词页
- 把它放进主关键词的 `aliases`

例如：

- `新能源`、`电车` 作为 `新能源汽车` 的 `aliases`
- `哇哈哈`、`宗馥莉`、`宗庆后` 作为 `娃哈哈` 的 `aliases`
- `杂粮汽车` 作为 `小米汽车` 的 `aliases`

### 3. 人物默认并入关键词层，不再做独立人物页

- `content/people` 负责存人物源数据
- 前台人物入口统一落到 `#/keywords/...`
- 导航里的 `人物` 只是关键词层里的一个自动分组，不是独立数据源
- 搜索里的 `人物` 结果也默认落到对应人物关键词页；只有找不到对应关键词时，才允许退回 `people/...`
- 自动规则：只要关键词被识别为人物，且被引用至少 `2` 次，就应自动进入 `#/people` 和侧边栏人物导航
- 如果人物只是服务于某个公司、品牌、家族或事件主线，优先并入上位关键词，不单独占关键词入口
- 如果人物本身在多期节目里已经形成独立讨论线，可以保留独立人物关键词，但仍然通过关键词页访问

判断标准：

- 问题核心是不是“这个人本身”
- 还是“这个人只是某个专题里的关键角色”

### 4. 上位词与下位词不要乱并列

- `汽车` 可以是上位词
- `新能源汽车` 是更具体的行业/产品专题
- `电车` 是更口语化、消费语境更强的表达

整理时优先选择最能代表该节目主线的那一个，不要同时堆多个高度重叠的泛词。

### 5. 单次出现的长尾词先不在关键词索引页展示

- 只出现 `1` 次的词可以保留在数据层，便于未来累计
- 但 `#/keywords` 列表页默认不展示
- 关键词索引页优先展示至少出现 `2` 次、已经形成节目群的词
- 人物导航也沿用这个门槛：至少出现 `2` 次的人物关键词才进入导航分组

### 6. 自动生成关键词文案不要写废话

- 不要写：
  - `XX相关关键词，聚合知识库里提到这个主题的N期节目`
- 应该写成一句真正有信息量的专题介绍

例如：

- `围绕房价的节目群入口，用来串联地产周期、政策压力和市场预期的相关讨论。`
- `围绕新加坡的节目群入口，用来串联其地缘位置、治理模式和区域博弈中的角色。`

### 7. 新整理节目时，先问自己这几个问题

1. 这个标签是不是已经属于现有专题？
2. 它是主入口，还是别名？
3. 它是独立专题，还是上位专题里的子人物 / 子问题？
4. 它现在只出现一次，是否值得先留在数据层、暂不放进列表页？

## 低质量写法黑名单

以下内容默认视为低质量，整理时要主动删掉或重写：

### 1. 整理者口吻

不要写：

- `这一期适合作为后续整理的入口`
- `后续可以沿着这个维度继续展开`
- `整理类似节目时可参考`

用户看到节目页，不应该读到整理后台备注。

### 2. 废话摘要

不要写：

- `本期讨论了……并进行了深入分析`
- `节目围绕……展开探讨`

必须把判断写出来。

### 3. 重复型观点

不要让 6 条 `viewpoints` 都在说同一件事。

如果标题和正文只是互相翻译，说明这条观点还没写开。

### 4. 空链接

- 空的 `people / themes / concepts / models / relatedEpisodes` 不要硬挂
- 但如果节目已经足够成熟，就应该主动补节点，而不是长期留空

### 5. 只显示不成体系

目标不是“页面上有东西”，而是：

- 节目能读
- 节点能点
- 节点之间能互相回跳
