## 这一篇管什么

B 站合集「颖漫谈（直播回放）」的整理流程和写作标准。直播和颖锐评是两套东西：颖锐评一期一个主题，直播一场两小时、覆盖三到五个互不相干的话题，所以数据结构、页面结构、写作要求都不一样。

前台入口是 `#/lives`，源数据在 `content/lives/`，与 `content/episodes/` 平级但独立。

## 目录与文件

- 原始字幕：`bilibili/live/[LIVEnnn】 标题.srt`，与颖锐评的 `bilibili/raw/` 分开放，避免 `buildEpisodeCatalog` 误扫
- 转写稿：`网页/workbench/LIVEnnn/LIVEnnn.transcript.txt`，去掉时间轴的纯文本
- 结构化稿：`网页/content/lives/LIVEnnn.json`
- 抽样复核记录：`网页/workbench/LIVEnnn/LIVEnnn.audit.md`

## 编号规则

按直播场次日期正序，不是按发布日期。LIVE001 是 2026-04-22 那场，LIVE027 是 2026-07-27 的加更场。同一天补发的几场按场次时间排。

**同一场被切成两段上传的，合并成一期。** 直播中途断线是常事，B 站上会出现同一天两个投稿（例如 LIVE028 是 07-29 的 21 点场加 23 点场）。判断标准是标题相同、时间相接。合并做法：
- `sessionLabel` 写成 `2026年07月29日 21点场与23点场（合并）`
- `durationMinutes` 两段相加
- `publishedAt` 取较早的那个投稿
- `videoLinks` 两条都留，按播出顺序排，**每条加 `"label": "21点场"` 这样的场次标签**。不加的话前端会渲染成两个一模一样的 bilibili 图标，读者分不清点哪个
- 转写稿合并成一份，中间插一行 `【以下为 23 点场，同日续播】` 作分隔

## 第一步：拿字幕

```bash
~/bilibili-downloader/.venv/bin/yt-dlp --cookies-from-browser chrome \
  --write-subs --sub-langs ai-zh --skip-download --no-update \
  -o "%(id)s.%(ext)s" "https://www.bilibili.com/video/<bvid>/"
```

合集里的 bvid 用这个接口取：

```bash
curl -s "https://api.bilibili.com/x/polymer/web-space/seasons_archives_list?mid=91741174&season_id=6621799&sort_reverse=false&page_num=1&page_size=30" \
  -H "User-Agent: Mozilla/5.0" -H "Referer: https://space.bilibili.com/91741174"
```

**字幕状态（2026-07-30 复核）**：28 期全部有转写稿。早期判定为无 AI 字幕轨的 6 期（LIVE003、LIVE004、LIVE011、LIVE019、LIVE023、LIVE025）由用户本地转录补齐。新场次先试 `--sub-langs ai-zh`，取不到再走本地转写。

**同时查这一场是不是充电专属**，决定网页上给蓝色还是金色入口：

```bash
curl -s "https://api.bilibili.com/x/web-interface/view?bvid=<bvid>" -H "User-Agent: Mozilla/5.0" \
  | python3 -c "import json,sys; d=json.load(sys.stdin)['data']; print('充电专属' if d.get('is_upower_exclusive') else '公开')"
```

充电专属的，`videoLinks` 里那条要加 `"access": "member"`，前端会渲染成金色会员入口。到 2026-07-30 为止，28 期里只有 LIVE027 加更场是公开视频，其余全是充电专属。

## 第二步：通读转写稿

一场 1.8 到 4 万字（时长 85 分钟到 160 分钟不等），主线程逐句读完再动笔，不派 subagent 代读。这条是质量的来源，也是用户定过的规矩（subagent 审稿只抓表面）。

## 第三步：写 JSON

### 两层结构

页面是三层折叠：大话题 → 小节 → 内容。数据里用 `segments[].chapter` 表示大话题，前端按相邻同名合并成组，默认全部收起。

```json
{
  "id": "LIVE024",
  "kind": "live",
  "title": "一周视频回顾，读评，深度分析，聊天",
  "sessionLabel": "2026年07月18日 21点场",
  "liveDate": "2026-07-18",
  "publishedAt": "2026-07-18T16:42:12.000Z",
  "durationMinutes": 132,
  "mainThread": "二十亿卖出去，二十亿买回来，技术留在了对面",
  "oneLiner": "抖音当年只肯出三千万美元买它的控股权。",
  "summary": "两到三段，只写重点",
  "videoLinks": [{ "platform": "bilibili", "url": "..." }],
  "tags": [],
  "boundaries": [],
  "segments": [
    {
      "chapter": "资本与公司：Manus 卖出去又买回来",
      "title": "三千万美元买断，抖音当时就是这么报价的",
      "summary": "一到两句",
      "points": ["...", "..."]
    }
  ],
  "audienceThreads": [{ "prompt": "口语化的问句", "reply": "分段展开" }],
  "themes": [], "concepts": [], "models": [], "relatedEpisodes": []
}
```

### 标题

`mainThread` 是整场标题，**照着 189 期节目的起名方式写**，不要写成短句白描。2026-07-29 统计过全部节目标题：平均 35 字，中位 33，51% 带问号，34% 带感叹号，58% 带数字，40% 带「真相 / 拆解 / 揭秘 / 戳破 / 背后 / 底层逻辑」。

常用句式（照抄结构就行）：

- 疑问加追问：`美伊协议谁赢了？油价为何没涨到300美元？`
- 断言加悬念：`车圈福威镖局凛冬已至！世界第一还是灭门？谁是青城派？`
- 现象加实则：`香港超瑞士、新加坡成全球离岸财富第一？实则只是溢出集散地。`
- 数字加撕开：`电车圈18亿巨亏撕开真相，……`
- 从 X 到 Y 加为什么：`从亩产万斤到高中生火箭：为什么越"严谨"的数据越容易骗人？`

**标点要按批次控配比，不是每条都加问号。** 51% 是全部 189 期里的比例，不是每条标题的写法。一批十条大约五条带问号、三条带感叹号、一条用冒号分层，剩下的写成纯断言。踩过的坑：一批十条写了九个问号，读起来像连环质问。

两条硬约束叠在一起：**句式往节目靠，但内容仍然只讲一个话题**。长不等于揉杂，节目那种长标题是同一件事的钩子、断言、悬念三层，不是三个话题拼在一起。字数落在 30 到 45 之间，别超过 80。

**加更场那类本身带内容标题的，直接用 B 站原标题。** 常规场次的投稿名是「一周视频回顾，读评，深度分析，聊天」，没有信息量，所以要自己起。但加更场的原标题往往已经是一串具体话题（例如 LIVE027 的「王虹回国？新加坡被骗；携程被罚；梁文锋录音；关门打狗DNA。」），这种照搬比自己概括更准，用户 2026-07-29 明确定过。判断标准：原标题不含「一周视频回顾 / 读评 / 深度分析」这几个词，就用原标题。

`oneLiner` 是列表页那句钩子，用来补标题没说完的那个细节，不要跟标题重复用词。整场标题也不要和某个小节标题重复用词。

### 大话题

分类词打头，格式是 `分类词：这一组讲什么`。分类词从下面这张表里选，跨期通用，不许一期一个说法：

国际局势 / 资本与公司 / 金融市场 / 产业观察 / 政企关系 / 科技与 AI / 社会心理 / 社会分层 / 舆论与评价 / 文化与规则 / 长期主义 / 国家路径 / 体育产业 / 个人选择 / 时代与个人 / 慈善与信任 / 教育与代际 / 城市与生活

一场分 3 到 6 个大话题。一个大话题只装一件事，名字要盖得住组里所有小节。禁止拿位置或动作当名字，「散场前聊了会儿球」这种不算主题，应该写成「体育产业：阿根廷怎么进的决赛」。

### 小节

一场 6 到 12 个小节，子标题要有钩子，例如「英国首相下台那天，对手夸了他一句」。段与段之间要有一条走得通的线。

每个小节 4 到 8 条要点。其中：

- 至少 2 条带句内链接，指向 `episodes` / `concepts` / `models` / `themes` / `lives`
- 最多 3 处 `**高亮**`，位置在句首、句中、句尾之间错开，不要每条都在同一位置
- 链接和高亮都分散在不同要点里，不许堆在最后一条

### 句内链接

写法是 `[显示文字](类型/id)`，前端只解析这种显式写法，不做全局关键词自动匹配。正文里满屏自动高亮会把页面弄花，这条是踩过坑的。

链接必须落在能读通的句子里，不要写成「串联：EP183、EP171」这种标签行。

### 直播间问答

3 到 5 条。问题标题写成观众口语化的问句（「手头钱不多，还能不能出去闯」），不要写成「有观众说……」的转述句。答案按主播原话展开到 200 字以上，分段写。

内容跟话题分段重复的问答直接删掉，只留独有的。空壳回答（「主播说得很清楚」）一律不要。

### 整理边界

至少写清楚这几条：这是即兴口播不是成稿节目；讳称与现实对象的对应是通行读法不是事实认定；哪些信息主播自陈是听说或揣测；字幕是 AI 转写、人名机构名按公开信息还原过；涉及投资的部分不构成建议。

### 文风

按 `~/.claude/protocols` 里那套 de-AI 规范：不用破折号，不用报幕句（「整场只讲一件事」「第三点是」「全场的落点」），具体主语加实义动词，短句，一句一个意思。

### 人称：无主语陈述

**正文里不出现指主播的人称。** 既不用「他说」「他的判断是」「他还补了一句」，也不用「我」。用户 2026-07-30 定的口径：这个网页是给这位 up 主做的，第三人称转述隔了一层，第一人称又不合适，因为做网页的人不是节目主角。

做法是把转述外壳去掉，直接陈述：

- 改前：`他说这跟传统文化关系不大，问题出在那句话的表述方式`
- 改后：`这跟传统文化关系不大，问题出在那句话的表述方式`
- 改前：`他的判断很直接：跟两千多万北京人一起要这个面，要得未免有点多`
- 改后：`判断很直接：跟两千多万北京人一起要这个面，要得未免有点多`
- 改前：`他自述一三年到一七年做过影视股权投资`
- 改后：`一三年到一七年做过影视股权投资`

**两个例外，必须保留：**

1. **节目里人物说的话原样保留**，包括引号内的第一人称。例：`因为当年岳不群说了：**我不把它交给我的孩子，我要把这个企业变成全民的企业**`。这个「我」是岳不群，不是主播。
2. **`boundaries` 整个不动**。整理边界是站在整理者角度写的说明（「他自陈是推测」「本页照录他的讲述」），用第三人称才对。

删掉主语之后每句都要重读一遍。批量替换最容易造成的破坏是把动词一起吞掉，2026-07-30 全库推平时出现过四十多处「他讲了X」变成「了X」、「他的X」变成「的X」的断句，全部要扫出来补回。

**不要贴标签式收尾。** 这是踩过的最大一个坑：2026-07-29 全库体检，180 段里有 100 段的最后一条要点写成了「这就是[某概念]」「这属于[某概念]那一类」「落到概念上是[某概念]」。单看每句都通顺，连起来读就是模板，每段结尾都要用一个概念升华一下，是最典型的 AI 文风。

链接必须落在有新增信息的句子里，让概念承担内容，而不是承担归类动作：

- 改前：`还会影响你的判断力，这属于[高价叙事](concepts/premium-narrative)那一类`
- 改后：`还会影响你的判断力。[高价叙事](concepts/premium-narrative)最贵的地方就是最后这一句`
- 改前：`就在原体系里换一个代言人，也就是[政权更替剧本](models/regime-replacement-playbook)`
- 改后：`就在原体系里换一个代言人。[政权更替剧本](models/regime-replacement-playbook)最关键的一步就是这个`

审计脚本已经加了 `labelTailMax`，一期最多容忍 3 处。写完一期先跑一遍，超了就逐条改写。

## 第四步：质量关卡

机器部分跑脚本：

```bash
node scripts/audit-lives.mjs
```

它检查破折号、报幕词、繁体字、字段完整性、大话题数量与命名、小节数量、要点条数、高亮上限、链接密度、问答字数、所有 id 是否存在。任何一条不过就返工。

人工部分三道：

1. **回字幕核对**：稿子里每个数字、人名、机构名、直接引述，逐条回 transcript 搜一遍。对不上就改，拿不准就写进整理边界
2. **结构自审**：这一场的逻辑线能不能一句话说清；十个子标题里有几个自己会想点开；链接是不是分散在不同要点里
3. **眼睛看**：构建后截图，看密度、留白、高亮位置是不是又排整齐了

截图用 headless Chrome（浏览器扩展没连上时的替代方案）：

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --window-size=1280,2000 --virtual-time-budget=9000 \
  --screenshot=out.png "http://127.0.0.1:4310/#/lives/LIVE024"
```

每批做完随机抽 20% 的要点回字幕复核。

**这一条到 2026-07-30 为止没有执行过**：28 期一个 `LIVEnnn.audit.md` 都没写，复核是在对话里做的，做完就散了。要么以后每期补上，要么把这条改成「复核结论写进当次提交信息」。眼下按后者执行，提交信息里要写清抽了多少条、查出什么、改了什么。

## 第五步：构建与互联

`npm run build` 会做三件跟直播有关的事：

1. 读 `content/lives/` 生成 `site.lives` 和 `stats.lives`
2. `buildLiveBacklinks` 扫描直播正文里的引用，反向挂到节目、概念、模型、主题上，写成 `liveMentions`。节目页、概念页因此长出「直播里聊过」区块。**这是自动生成的，不要手工去改 189 个 EP 的 JSON**
3. 直播作为 `live` 类型节点进知识图谱，与被引用的节点建边
4. 首页节目区按发布时间混排节目和直播，新场次自动排到最前面，卡片编号显示为「直播028」

构建通过之后按 `sop/06-发布命令与验收.md` 推送：

```bash
git add content/lives docs/data docs/assets docs/index.html
git commit -m "..."
git push yinfluence-origin main        # 不是 origin，origin 指向的仓库没有写权限
```

## 第六步：新场次怎么被发现

`scripts/scan-new-lives.py` 扫合集 6621799，按 bvid 跟 `content/lives/` 比对，发现新增就下字幕、生成转写稿、写 `workbench/pending-lives.json`。同一场切成两段的（标题相同、发布时间差两小时内）会自动合并成一条待办。

```bash
python3 scripts/scan-new-lives.py --dry-run   # 只报告有没有新场次
python3 scripts/scan-new-lives.py             # 备料
```

`scripts/auto-daily.sh` 每次被唤起都会顺带跑一次这个脚本，所以不用手动记着扫。

**为什么直播不能跟节目共用一个扫描窗口**：节目在北京 19 到 21 点发，auto-daily 的窗口是 UTC 12:05 到 14:30 对着这个时间设的。直播回放是次日凌晨到清晨才传，28 场实测集中在 UTC 15 到 17 点（北京 23:00 到次日 01:00），一场都落不进节目那个窗口。所以直播走独立分支，不受 `today_done()` 那个当天收工开关影响。

**脚本只备料，不整理。** 整理要逐句通读两三万字转写稿，是第二步定死的规矩，不交给无人值守的 agent。脚本备完料会弹一条通知，剩下的在对话里做。

## 已知的坑

- 直播的 `tags` 不进关键词管线。`buildKeywordCatalog` 只吃 `episode.tags`，前端有十多处假设 id 是 EPxxx，硬接进去回归面太大。所以标签只显示已经存在于关键词库里的那些，其余不显示，避免出现点不动的假按钮。**代价是首页卡片上直播的标签明显比节目少**：28 期共 400 多个 tag，只有四成在关键词库里，像「林语堂」「梁文锋」「DeepSeek」这些都显示不出来。要打通得先处理关键词页和搜索的回归面
- 首页卡片的摘要取 `live.summary` 不是 `oneLiner`。`oneLiner` 是列表页用的一句话钩子，放到首页会显得比节目卡片单薄一大截
- `bilibili/live/` 要和 `bilibili/raw/` 分开。`buildEpisodeCatalog` 只匹配 `[EPxxx】`，混放会让语义变糊
- 同名大话题只在相邻时合并。不相邻的同名会打乱顺序，命名时避免重复
