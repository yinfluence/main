## 目标

新一期节目从 B 站/YouTube 发布，到网站上线，尽量少人工。把整条流水线拆成「机械活」和「判断活」两类：机械活全部脚本化、可无人跑；判断活（内容创作）留给对话里的整理者（LLM）。

## 流水线全景（新一期从发布到上线）

| 步 | 动作 | 谁做 | 无人自动 |
| --- | --- | --- | --- |
| 1 | 扫 B 站 UP 投稿列表，发现新 EP 号 | `scan-new-episodes.py` | ✅ |
| 2 | 判断会员/非会员、取发布时间 | 同上 | ✅ |
| 3 | 下载 AI 字幕存 `raw/`（充电后会员也能下） | 同上（调 `fetch-ai-subtitle.py`） | ✅ |
| 4 | `npm run srt` 生成草稿 JSON | 同上 | ✅ |
| 5 | 写 `summary/topic/viewpoints` | **整理者（LLM）** | ❌ |
| 6 | 抽概念/模型、判断影射写边界声明 | **整理者（LLM）** | ❌ |
| 7 | 建关键词词条、双向回填、写网页日志 | **整理者（LLM）** | ❌ |
| 8 | 字数自检、繁体扫描 | 脚本 | ✅ |
| 9 | `npm run build` + `test:ui` | 脚本 | ✅ |
| 10 | `git commit` + `npm run ship`（push+deploy+线上 md5 验证一体） | 脚本 | ✅ |
| 11 | 外层 `verify_online` 独立复核线上（不信 agent 报告） | 脚本 | ✅ |

**唯一必须有 LLM 的是第 5–7 步**（判断性内容创作）。这是整条流水线的核心约束：cron 脚本再全，也写不出 summary、判断不了影射边界。

## 两种运行模式

### 模式 B（推荐）：定时备料 + 一句话触发

- **每天 20:10（中国时间 = UTC 12:10）**，cron 跑 `scan-new-episodes.py`：发现新期 → 下字幕 → 生成草稿 → 写 `workbench/pending-episodes.json` → 发系统通知/推送「EPxxx 已就绪，字幕已下载，来喊我整理」。
- 用户看到通知，在对话里说一句「整理新一期 / 网页更新了」。
- 整理者（LLM）：读 `workbench/pending-episodes.json` + transcript → 完成第 5–7 步 → build → push → 线上验证 → 回报「EPxxx 已上线」。
- 优点：机械活全自动、用户零操作就备好料；内容由 LLM 在线整理，质量可控（字幕错字校对、影射边界判断都在）。缺点：需要用户一句话。

### 模式 A（最大化自动化）：定时唤起 LLM 全自动

- 用 Claude Code 的 `schedule`（定时 cloud agent）每天 20:10 唤起整理者。
- 整理者自己跑 `scan-new-episodes.py`，有新期就完成第 5–11 步全流程并上线，发通知；无新期静默退出。
- 优点：真正无人值守。缺点：全自动上线，若 LLM 对影射边界/字幕错字判断失误直接上线无人审；依赖 `schedule` 可用 + cookie 不过期。

### 模式 D（当前在用）：launchd 定时唤起本机 claude 全自动

- `~/Library/LaunchAgents/com.yingxiangli.daily-auto.plist` 定时跑 `scripts/auto-daily.sh`：扫描 → 有新期则以 `scripts/daily-agent-prompt.md` 唤起 headless claude 完成整理、build、push、三步验证；无新期静默退出。日志在 `logs/auto-daily-YYYY-MM-DD.log`。
- 发布规律（2026-07-30 用 `publishedAt` 时间戳按 `zoneinfo` 重算最近 12 期）：北京 19:00 整 10 期、20:00 整 1 期（EP185）、20:50 一期（EP188）。**19 点档从 EP177（07-06）起已成主流**。注意 B 站页面按浏览器时区渲染，英国夏令时（BST）与北京差 7 小时不是 8，容易把北京 19:00 误读成 20:00。
- 调度（2026-07-30 定稿，起点按用户要求对齐北京 20:10 与 20:20）：launchd 每天英国本地 `12:10 / 12:20 / 13:10 / 13:20` 各触发一次——`12:xx` 对应冬季 GMT 的北京 20:10/20:20，`13:xx` 对应夏季 BST 的同一时刻；打偏的那两个会被窗口判断或锁挡掉。外加英国本地 `16:00 / 18:00 / 19:00 / 20:00` 四个当天补救点（整理卡死后重新拾起草稿用，同时是直播回放唯一的扫描机会），以及开机 RunAtLoad 补捞。后两个是 2026-08-02 补的，理由见下面的直播扫描时机。
- 密集扫描靠窗口循环不靠启动点个数：脚本在 UTC 10:50–14:30（北京 18:50–22:30）窗口内每 10 分钟重扫，扫到新期整理完即停；窗口外触发只扫一次。夏季 `12:10` 落在北京 19:10，正好接住 19 点档；冬季最早是北京 20:10，19 点档要晚 70 分钟。
- 止损与自我监督（2026-07-30 加，起因见下）：
  1. **锁带 PID 和出生时间**。进程已不在或超过 2 小时即判僵死锁清掉。以前是纯目录锁靠 `trap` 清理，claude 被 `kill -9` 或休眠打断就留下死锁，之后每次触发都被挡在门外，整个自动化静默死亡。
  2. **整理进程有看护**。日志连续 15 分钟没有新字节判卡死，总时长超 60 分钟判超时，两种都连子进程一起杀（`kill_tree`）。以前是裸调用 `claude -p`，挂住就无限等且全程占锁。
  3. **失败当场重试**。整理失败返回 20，隔 5 分钟重试，最多 2 次；用完仍失败就留草稿等下一个触发点。不干等下一次 launchd——卡在当天最后一个点就要等 24 小时。
  4. **草稿不算已收录**。`local_eps()` 只认整理完成的（判 `summary` 不判 `status`，早期 53 期没有 `status` 字段）。以前只看文件名，整理一卡死草稿就被当"已收录"，那一期永久冻在待整理且无人知道。`today_done()` 同样不被草稿骗到，否则当天补救通道被堵死。
  5. **一天只有一期**：库里最新一期 `publishedAt` 已是当天（UTC）且已整理完成，就当天收工不再扫。**收工只收节目那条线**——脚本把结果记在 `EPISODES_DONE`，跳过节目扫描后仍然跑一次 `scan_lives`，不能裸 `exit 0`（2026-08-02 修，起因见事故记录）。
  6. **直播扫描的时机是独立问题**（2026-08-02 加）。节目窗口内不扫直播，全天扫直播的机会只有：节目窗口跑完那一次、窗口外每个 launchd 触发点、以及收工分支。直播回放实测集中在 UTC 15–17 点上传（北京 23:00–01:00），所以补救点必须盖住这一段并留尾巴——英国本地 `16:00 / 18:00 / 19:00 / 20:00` 夏令时等于 UTC `15/17/18/19` 点。冬令时整体后移一小时，尾巴也够。
- 事故记录：2026-08-01 直播 LIVE029（8月1日21点场）漏扫，隔 21 小时才被发现，是用户问「为什么节目更新了网站没更新」才查出来的。三个原因叠加：
  1. **合集接口的收录晚于投稿发布**。那场的 `pubdate` 是英国本地 17:41，当天最后一个触发点 18:00 扫的时候合集里还是 29 个，什么都没看到。差了 19 分钟还扫不到，说明 `seasons_archives_list` 不是投稿一发就更新。延迟具体多久没测过，所以补救点要往后铺，不能卡着上传时段收尾。
  2. **8-02 全天的触发点都落在节目窗口内**，而窗口循环里不调 `scan_lives`，只有跑完整个窗口才扫一次。
  3. **`today_done` 命中时直接 `exit 0`**，连直播都不扫。而代码注释当时明明写着「直播由 scan_lives 独立判断，不受这个开关影响」，**注释描述的是意图，代码干的是另一回事**。
  修法：`EPISODES_DONE` 标志 + 补两个 launchd 触发点（本地 19:00 / 20:00）+ `test:auto` 加一条断言（收工当天仍然扫直播），这条断言在旧代码下必然失败。
- 事故记录：2026-07-29 与 07-30 连续三次扫描全失败（`isLogin=false`），EP190 晚一天才上线。双重原因——Chrome 磁盘 cookie 滞后于内存导致导出的是已轮换的旧 SESSDATA；原窗口 20:05 起系统性错过 19 点档。失败通知走 `display notification` 被系统静默丢弃、`osascript` 照样返回 0，所以两天无人察觉。

### 模式 C（最简）：纯一句话触发，无定时

- 不设 cron。用户想更新时说「检查网页更新」，整理者跑扫描 → 有新期就整理上线并回报，无则回「暂无新一期」。

## 触发词（整理者识别）

用户说以下任一，整理者执行「扫描 → 若有新期则备料 → 整理 → 上线 → 回报」：

- 「网页更新了 / 网页是否有更新 / 检查更新 / 有没有新一期 / 整理新一期 / 自动跑一下」

## 扫描的盲区：节目可能先发 YouTube

`scan-new-episodes.py` 原本只抓 B 站 UP 主投稿列表（`x/space/wbi/arc/search`，mid 91741174），**YouTube 那条线完全没有监控**。2026-08-02 起已经补上，下面是起因和现在的口径。

EP192 就是这么漏的。当天 YouTube 上已经发布（UTC 10:00），B 站直到当晚都没有对应投稿，脚本每十分钟扫一次，每次都报「无新一期，UP 投稿最新 EP191 已收录」。日志、状态文件、线上数据三处都显示一切正常，因为它们问的是同一个数据源。用户看到新节目来问，才发现盲的是数据源不是脚本。**一个数据源的自动化，报出来的正常只对那个数据源有效。**

现在 `scan-new-episodes.py` 会先抓 B 站，再抓 YouTube 频道 RSS（`UCLELZILGdldscrt7VggJaRQ`），两边并集去比对本地期号。B 站有的以 B 站为准，只在 YouTube 上的照样报出来并写进 `workbench/pending-episodes.json`，带 `"source": "youtube"`。这类期的字幕拿不到 B 站接口，备料那步会跳过，转写和整理留给对话里的整理者。

RSS 不需要 cookie，也不受 B 站风控影响，所以它同时是 cookie 失效时的兜底通道。手动核对时可以直接看：

```bash
python3 scripts/scan-new-episodes.py --dry-run   # 两个平台一起判断
curl -s "https://www.youtube.com/feeds/videos.xml?channel_id=UCLELZILGdldscrt7VggJaRQ" \
  | grep -oE "<title>[^<]+</title>" | head -5
```

`videoLinks` 允许只有 YouTube 一条。B 站补发之后再把 bilibili 链接加回去，`scripts/sync-video-links.mjs` 和 `scripts/video-link-overrides.json` 都支持这种后补。

## 关键约束（决定自动化能不能长期跑）

1. **颖响力充电必须保持有效**。充电后会员视频 `player/wbi/v2` 才返回字幕轨（见 `sop/02`）；过期则新会员期字幕又拿不到、脚本第 3 步失败。
2. **B 站 cookie 会过期，而且"Chrome 里登录着"不等于"导出的 cookie 有效"**。脚本从 Chrome 现导，但 yt-dlp 读的是磁盘上的 Cookies 库，Chrome 运行时新 SESSDATA 还留在内存里，导出的可能是已轮换的旧值——2026-07-29/30 的事故就是这个。现在的应对：导出前先删旧临时文件（否则 yt-dlp 失败会静默复用过期 cookie）、校验文件里真有 `SESSDATA`、登录态无效则隔 25 秒重导最多 3 次给 Chrome 落盘时间、都不行再退到手工存的长效 cookie `scripts/.bili-cookies.txt`。全都失败才以退出码 1 + 可操作提示停下，不会静默产出脏数据。修复办法通常就是在 Chrome 里打开一次 bilibili.com 刷新登录态。
5. **失败状态只落盘，不弹窗不发通知**（用户 2026-07-30 决定）。`logs/status.json` 是最近一次结果，`consecutive_failures` 字段一眼看出连败几次；历史在 `logs/status-history.jsonl`。原因：`display notification` 的请求被系统静默丢掉而 `osascript` 仍返回 0，弹窗虽然能看见但抢焦点。**所以"网站更新了吗"这类问题先读 `status.json`，别只看日志。**
3. **影射类节目仍需人工判断边界**。凡标题/内容用《笑傲江湖》等化名影射（如 EP153/170/187），整理者必须写「化名影射、非事实指控」的边界声明，这一步不可全自动省略。
4. **AI 字幕同音错字**必须对照修正（「颖响力」→「影响力」、「大棋」→「大旗」、「小厮」↔「小斯/小司」等）。
