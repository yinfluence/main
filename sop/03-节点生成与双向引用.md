## 双向引用同步规则（concepts / models / themes）

新节目写入时，最常见的隐性缺陷是**单向引用断裂**：
`content/episodes/EPxxx.json` 的 `concepts / models / themes` 数组里写了 `moral-capital` 这种 ID，但对应的 `content/concepts/moral-capital.json` 的 `episodes` 数组里没有把 `EPxxx` 写回去。
结果：图谱链接是双向的（build 时两边都注册），但**概念/模型/主题详情页**只渲染该词条 JSON 里的 `episodes` 数组——前台会出现"该概念明明被 EP145 用了，详情页却只列 EP070"的断裂。

硬规则：

- 节目 JSON 的 `concepts / models / themes` 里每写一个 ID，**必须同步**到对应词条 JSON 的 `episodes` 数组里。落库前自检，不能依赖构建脚本兜底。
- 同步条目格式：`{ "id": "EPxxx", "note": "这期怎样使用该 concept/model/theme，1-2 句话" }`。`note` 不许留空——空 `note` 等于把读者推回去翻原 EP，违背了"详情页要替读者回答'为什么和这一期相关'"的目的。
- 概念/模型/主题 JSON 的 `episodes` 数组按 EP 编号升序排列。
- 一次性历史同步（2026-05-22 已完成）补的是空 `note` 占位条目，**必须后续逐条回写真实 `note`**；不是补完就完事。回写顺序按 EP 新旧倒序、按 `note` 空缺数量优先。
- 审计命令：`python3 -c "...扫 episode.<field> vs <kind>/<id>.episodes 缺漏..."`（参考 `/tmp/sync_backlinks.py`）。每次新写一期节目，落库前跑一次审计，缺漏数应为 0。

为什么不让 build 脚本自动合并：build 里合并出来的"相关 EP"没有 `note`，前台无从展示"为什么相关"。`note` 是人工策展，必须沉淀回源 JSON，不能放进运行时。

## 节点生成硬标准

这一节不是写作建议，而是实际落库时必须遵守的标准。

### 1. 新增节点前，先查有没有现成节点

不要看到一个新说法就立刻新建 `concept` 或 `model`。

这是默认规则，不是可选动作。

先做两步搜索：

```bash
rg -n "咽喉|命门|海峡|中立" content/concepts content/models
rg -n "英文 slug|拼音 slug|中文近义词|英文常用名" content/concepts content/models content/themes content/people content/keywords
```

判断顺序：

1. 如果只是同一机制的另一种说法，优先复用已有节点
2. 如果只是当前节目的一次性表达，先留在 `summary / topic / viewpoints`
3. 只有当它能跨节目复用、且现有节点明显装不下时，才新增节点

复用已有节点的收益要写死理解：

- 省时间，不重复造轮子
- 提高整理效率，不用每期都发明新概念、新模型
- 让原有节点越用越厚，`episodes / context / related*` 会越来越完整
- 让知识库入口更稳定，读者更容易形成连续认知，不会被一堆近义新词打散

所以默认动作永远是：

`先查旧节点 -> 能复用就复用 -> 复用后把旧节点补厚`

而不是：

`先新建一个差不多的新节点 -> 再想办法解释它和旧节点有什么区别`

### 2. 概念和模型怎么区分

概念回答：

- `这里到底出现了什么现象？`

模型回答：

- `这些现象背后反复出现的机制是什么？`

快判断：

- 能用一句话定义某个稳定现象，优先做 `concept`
- 需要把多个概念串成因果结构，优先做 `model`
- 如果它暂时只能解释这一集，先不要建节点

### 3. 不同关联字段，用的不是同一套键

这是当前项目最容易填错的地方。

- `episode.concepts` 填 `concept.id`
- `episode.models` 填 `model.id`
- `episode.people` 填人物 `name`，不是人物文件名
- `episode.themes` 填主题 `name`，不是主题文件名
- `episode.relatedEpisodes` 填 `EPxxx`
- `episode.tags` 填自然语言关键词，关键词页主要靠这里驱动

也就是说：

- 概念 / 模型：节目里用英文 slug `id`
- 人物 / 主题：节目里用中文展示名 `name`
- 关键词：不在节目 JSON 单独挂 `keywords` 字段，主要通过 `tags` 进入关键词系统

### 4. 关键词关联怎么生效

关键词层和其他节点不一样。

当前构建逻辑是：

1. 先从每个节目的 `tags` 自动生成关键词目录
2. 再把 `content/people/*.json` 自动并入关键词目录，人物会继承 `id / englishName / aliases / episodes`
3. 最后把 `content/keywords/*.json` 里的人工条目与前两层结果按 `name / aliases` 合并

所以：

- 想让某期进入某个关键词专题，首先检查 `episode.tags`
- 想让某个人物稳定进入关键词系统，先维护 `content/people/*.json`
- 如果只是同义词、口语词、下位词，不新增新关键词页，放进主关键词的 `aliases`
- 只有确实需要一个稳定专题入口时，才新建 `content/keywords/*.json`

### 4.1 `aliases` 和 `relatedKeywords` 不是一回事

- `aliases`
  - 表示同一个关键词的别名、口语、旧 slug、常见误写
  - 前台仍然落到同一个关键词页
- `relatedKeywords`
  - 表示两个关键词应该互相链接，但不应被视为同一个词
  - 前台要在关键词页显式展示“相关关键词”

判断标准：

- 如果用户搜索后应该进入同一个页面，用 `aliases`
- 如果用户点进去后应该看到不同页面，但两者需要互相跳转，用 `relatedKeywords`

例如：

- `新能源` / `电车` -> `新能源汽车`
  - 用 `aliases`
- `保险` / `保险公司` / `香港保险`
  - 不是同一个词
  - 应该各自保留页面
  - 但必须互相写进 `relatedKeywords`

### 4.2 构建阶段的关键词联动机制

- 构建时必须保留人工写入的 `relatedKeywords`
- 人工写入的 `relatedKeywords` 默认按双向关系处理
  - 例如在 `新加坡` 里写了 `黄循财`
  - 构建后 `黄循财` 也应自动反向出现 `新加坡`
- 构建时还要自动补一层“相近词联动”，而且这是主机制，不是附属点缀
- 自动联动至少覆盖三类：
  - 名称或别名互相包含
  - 明显的上位词 / 下位词
  - 同期节目高重合 / 高共现的关键词
- 已有 `parents` 关系也必须推出上下位连接
- 自动联动是主路径，人工 `relatedKeywords` 只负责：
  - 补足机器不容易看出来的关系
  - 修正高价值但低文本相似度的关系
- 一旦发现自动联动不够，必须回到 `content/keywords/*.json` 手工补 `relatedKeywords`

### 4.3 保险类词是第一组硬样例

以下三类词必须彼此联动，作为关键词联动机制的基准样例：

- `保险`
- `保险公司`
- `香港保险`

要求：

- 三者必须各自保留独立关键词页
- 三者必须互相出现在 `相关关键词`
- 后续新增类似词，例如 `航运保险`、`战争险`、`再保险` 时，也必须按同样规则处理：
  - 先判断是否独立成页
  - 如果独立，就补进相关词网络

### 5. `episodes[].note` 怎么写

无论是概念、模型、人物、主题还是关键词里的 `episodes` 数组，`note` 都不要写成摘要复读。

正确写法：

- 说明这期为什么和这个节点有关
- 说明它承接的是哪一个判断或哪一种机制

错误写法：

- `本期讨论了这个概念`
- `这期和这个模型有关`

正确方向：

- `节目把维文的表态视作小国守住规则边界的典型表达`
- `节目把保险、护航和定价权合并解释为海峡秩序的一部分`

### 6. 模型的 `sourceLabel / sourcePath` 规则

模型条目必须明确自己是本地颖响力模型，还是复用 GV 现有模型。

如果是本地颖响力模型：

- `sourceLabel`: `颖响力模型：模型中文名`
- `sourcePath`: 当前模型 JSON 的绝对路径

如果是复用 GV 模型：

- `sourceLabel`: `GV 模型：模型中文名`
- `sourcePath`: 指向 GV 原始模型卡路径

不要空着这两个字段，也不要随便写一句说明文字代替。

### 8. 从节目到节点的回填顺序

标准顺序固定为：

1. 先把 `content/episodes/EPxxx.json` 写完整
2. 再决定哪些内容值得沉淀成 `concepts / models / people / themes / keywords`
3. 新建或复用节点后，先把该节点自己的 `episodes` 和 `related*` 补齐
4. 再回填节目里的：
   - `concepts`
   - `models`
   - `people`
   - `themes`
   - `relatedEpisodes`
5. 最后跑 `npm run build` 验证网页跳转

不要先建一堆节点，再倒推节目内容。

### 9. 新节目如何接入旧知识库

这一步必须显式做，不能只把新节目写完就停。

每来一集新节目，都要回答同一个问题：

`这期内容应该挂回旧库里的哪些节点？哪些词要复用，哪些词要新建，哪些词之间需要补链接？`

标准流程固定为：

1. 先写新节目的核心结构
   - 完成 `content/episodes/EPxxx.json` 的：
     - `summary`
     - `topic`
     - `viewpoints`
     - `extensions`
   - 先把这一期真正讲了什么说清楚，再决定知识库链接

2. 再做“旧节点搜索”，不要凭记忆
   - 至少查：
     - `content/concepts`
     - `content/models`
     - `content/people`
     - `content/themes`
     - `content/keywords`
   - 推荐先用：

```bash
rg -n "关键词A|关键词B|关键词C" content/concepts content/models content/people content/themes content/keywords
```

3. 对每一个新出现的重要词，强制做三选一判断
   - `并入 aliases`
     - 如果它只是旧关键词的别名、旧写法、口语词、戏称
   - `并入 relatedKeywords`
     - 如果它和旧关键词不是同一个词，但应该互相跳转
     - 典型情况：
       - 上位词 / 下位词
       - 同一议题簇里的近邻词
       - 人物 / 国家 / 公司 / 产品之间的稳定专题关系
   - `新建独立节点`
     - 只有当它已经足够稳定，能承接未来多期节目时才新建

4. 先补节目到旧库的正向链接
   - 回填新节目的：
     - `concepts`
     - `models`
     - `people`
     - `themes`
     - `tags`
     - `relatedEpisodes`
   - 这一层决定新节目怎样进入旧知识网

5. 再补旧节点到新节目的反向链接
   - 对被命中的概念 / 模型 / 人物 / 主题 / 关键词：
     - 把 `EPxxx` 写进对应节点的 `episodes`
     - `note` 说明这期为什么和它有关
   - 不允许只有节目单向引用旧节点，而旧节点不记这期

6. 最后补词与词之间的联动
   - 如果新节目带来了新的词簇关系，必须补到 `content/keywords/*.json`
   - 优先补：
     - `aliases`
     - `relatedKeywords`
     - 必要时 `parents`

7. 最后验证“点进去之后能不能顺着走”
   - 至少自己检查：
     - 从新节目点进关键词
     - 从关键词点回相关节目
     - 从关键词点到相关关键词
     - 从人物/国家/公司这种词簇里能不能继续横向跳

#### 9.1 一个新节目接入旧库时，最少要补哪几种链接

每期至少检查这五类：

1. 这期对应哪些旧节目
   - 填 `relatedEpisodes`

2. 这期对应哪些旧概念 / 旧模型
   - 复用旧 `concepts / models`

3. 这期对应哪些旧人物 / 旧主题
   - 回填 `people / themes`

4. 这期带来的关键词，应该并入哪个旧关键词
   - 能并入 `aliases` 就不要新开页

5. 这期新增的关键词关系，是否需要补 `relatedKeywords`
   - 只要两个词不是同一页、但用户应该能互相跳，就补

#### 9.2 `relatedKeywords` 的使用标准

不要把 `relatedKeywords` 当装饰字段。

它的职责是：

- 把本来分散的近邻词重新织回知识网
- 避免用户搜到一个词后，永远停在单页里

必须优先补 `relatedKeywords` 的情况：

- 上位词 / 下位词
  - 例如：
    - `保险` ↔ `保险公司`
    - `新能源汽车` ↔ `小米汽车`
- 国家 / 核心人物 / 关键制度
  - 例如：
    - `新加坡` ↔ `黄循财 / 李显龙 / 维文 / 组屋`
- 议题主词 / 关键载体
  - 例如：
    - `伊朗` ↔ `霍尔木兹海峡 / 哈梅内伊`

#### 9.2.1 新节目带来的高价值新关键词必须写独立词条（硬规则）

每期新 EP 进入知识库时，整理者必须主动判断本期带来的新名词里哪些属于"高价值新关键词"，并在 `content/keywords/` 写独立 JSON 词条。这是**硬规则**，不允许只把这些名词扔进节目 `tags` 让构建脚本自动生成空页面。

高价值新关键词的判定（满足任一即必须独立成页）：

- 案件 / 事件 / 风波中的**核心人物**：例如团伙头目、案件被告主嫌、官司当事人、新出场的主要分析对象。即使只在单期出现，节目用它承担了完整身份解释和判断负载，就必须成页。
- 案件 / 事件 / 风波中的**核心组织 / 群组 / 平台**：例如团伙加密群名、新爆雷的公司、新被点名的机构、首次出现的关键品牌。
- 节目**反复使用的人格/机制概念词**：例如"精致利己主义""影子舰队""粉底液将军""灰色石油网络"这类节目用来概括一类现象的词，即便首次出现也要建词条，方便后续节目复用。
- 节目对外**点名**的高识别度专有名词：通常带有人物姓名、学校名、城市名、机构名、暗语体系等，构成读者搜索该 EP 时的第一个入口词。

不属于高价值的处理方式：

- 普通修饰词、口语表达、单期一次性形容 → 留在节目正文，不进 `tags`、不建词条。
- 已有词条的同义词 / 别名 / 旧写法 / 缩写 → 加进对应 `aliases`，不新开页。
- 已有词条的下位词、近邻词 → 写进对应 `relatedKeywords`，不新开页。

写入要求：

- 必须按 SOP 关键词类型规格选定 `kind`（`person / organization / event / concept / mechanism / asset / geography / product / theme / general`），按该类型字段写满，**不允许只写 `summary + description` 就交差**。
- 人物 / 组织 / 事件类涉及现代职务、量刑、组织状态时，必须写 `asOf`；外部事实必须列 `sources`，无法核对时正文改成"节目转述媒体报道"等归因表达，不能伪装成外部事实。
- 顶层 `episodes` 必须包含本期，且 `note` 写清这期怎样使用该词条，不能留空。
- 同步在节目 JSON 的 `tags` 数组里出现该词。`tags` 与 `content/keywords/<slug>.json` 必须双向存在——只有 `tags` 没有词条 = 构建出空页；只有词条没有 `tags` = 词条与本期断联。

判定流程（每期固定执行）：

1. 完成节目 JSON 主体后，列出本期所有出现的人名、组织名、群组名、地点名、概念词、暗语体系、量刑词。
2. 对每个词执行三选一：`并入已有词条 aliases` / `新建独立词条` / `只留正文不进 tags`。
3. 对判定为"新建独立词条"的词，逐个写 `content/keywords/<slug>.json`，按类型字段写满。
4. 把所有要进入关键词系统的词同步加入节目 `tags`。
5. 跑 `npm run build`，确认每个新词的页面真的渲染了内容（不是空模板兜底）。

未执行此节即视为本期未整理完毕，不允许进入 build + 日志 + 发布步骤。

#### 9.3 新节目接入后，必须做的最终检查

每次新节目接入后，至少做一次：

```bash
npm run build
```

然后人工检查：

- 新节目的详情页是否已经挂回旧库
- 被命中的关键词页是否已经出现这期
- 相关关键词是否已经能互相跳转
- 是否还有明显孤立词没有被并回旧知识网

## 节点层怎么补

### 总原则

不是为了让“关联概念 / 关联模型 / 关联人物 / 关联主题”显示出来才去补节点。

而是因为：

- 这个节点真的能跨节目复用
- 它不是只服务这一集
- 它值得作为独立入口存在

### 概念怎么抽

概念比模型更小，回答的是：

- 这里到底出现了什么现象？

判断标准：

- 是否能用一句话定义
- 是否可能在别的节目再次出现
- 是否比节目标题更稳定

例如：

- `价格发现延迟`
- `隐形债务`
- `公司身份迁移`
- `语言工具化`

### 模型怎么抽

模型比概念更高一层，回答的是：

- 这些现象背后反复出现的机制是什么？

模型应该比概念更少、更稳。

优先复用已有模型：

- `路径依赖`
- `委托代理问题`
- `反馈回路`

如果已有模型不够，再新增新的中层模型。

例如：

- `资产负债表维持`
- `风险转移链条`
- `制度适配`

### 人物怎么补

只有人物真的构成该期的重要角色时才补。

不要因为 transcript 里提了一次名字就强行建人。

适合补人物的情况：

- 人是这期判断的关键载体
- 这个人在多期节目中重复出现
- 用户点进去确实会想知道“他是谁、为什么重要”

### 主题怎么补

主题是跨多期的议题层，不是标签升级版。

一个主题应该回答：

- 这些节目为什么应该被放到一起看

例如：

- `房地产去杠杆与风险出清`
- `价格托底与账面维稳`
- `AI创业、资本主场与公司身份`
- `小国平衡与地缘生存`
