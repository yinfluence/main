## 视频链接维护标准

视频链接现在是节目页标配，不是可有可无的附加信息。

### 标题基准与跨平台对照

节目页 `title` 必须以 YouTube 视频标题为主基准：

1. 先读取对应 YouTube 链接的真实标题。
2. 取第一个 `｜` 之前的内容作为网页节目标题。
3. 不要把 `｜` 后面的关键词串写进 `title`。
4. 不要为了知识库整理把节目标题改写成摘要式、概念式或编辑版标题。
5. 只有在 YouTube 标题明显错误、用户明确要求改成另一版标题时，才偏离这个规则，并在提交说明里写清楚。

B 站链接匹配必须先用官方 B 站列表 / 合集和 YouTube 主标题做对照，不能只用当前网页标题搜索。原因是网页标题一旦被整理成短标题或概念标题，就会导致 B 站搜索漏匹配，进而把真实存在的视频误标成 `已下架`。

更新 B 站链接时按这个顺序：

1. 先用 EP 编号匹配 B 站标题里的 `【EPxxx】`。
2. 没有 EP 编号时，用 YouTube 主标题和 B 站标题的主标题做规范化匹配。
3. 对新节目或人工给出的 B 站链接，必须直接查 BV 对应的 `https://api.bilibili.com/x/web-interface/view?bvid=...` 响应，不能只看页面颜色或当前覆盖表。
4. 如果响应里 `is_upower_exclusive === true`、合集匹配条目的 `attribute === 8`，或 B 站条目标记为 `充电专属`，写入 `"access": "member"`。
5. 只要找到确定链接，就同时更新 `content/episodes/EPxxx.json` 和 `scripts/video-link-overrides.json`；会员节目覆盖表不能只写 `url`，必须同步写 `access: "member"`。
6. 只有检查过官方列表 / 投稿页 / 充电专属入口仍没有确定结果后，才能保留或写入 `status: "unavailable"` + `note: "已下架"`。

### 当前协作输入边界

当前最稳的协作方式是：用户提供新节目的 `YouTube 链接`、`B 站链接` 和 `完整字幕 / 纯文字稿`，整理者负责后续全部知识库动作。

用户需要提供：

1. YouTube 链接
2. B 站链接
   - 如果是会员 / 充电 / 动态入口，优先直接给真实链接
   - 如果 B 站暂未上架，明确说明 `暂未上架`
3. 完整字幕或纯文字稿
   - NotebookLM、手工转写、闪电说、其他 ASR 产出的纯文字都可以
   - 只要没有标准时间轴，就保存为 `.md`，不要伪造 `.srt`

用户提供 B 站链接后的硬规则：

1. 不允许把“用户给了链接”直接等同于普通节目。
2. 第一动作必须提取 BV 号，并查 `https://api.bilibili.com/x/web-interface/view?bvid=...`。
3. 必须明确判断这条链接是会员节目还是非会员节目，再写入网页数据。
4. 如果接口里 `is_upower_exclusive === true`，或合集里当前 `bvid` 对应条目 `attribute === 8`，必须按会员节目处理。
5. 会员节目必须同时写入 `content/episodes/EPxxx.json` 和 `scripts/video-link-overrides.json` 的 `"access": "member"`。
6. 只有完成上述检查后，才允许在网页日志里写“普通视频”或“会员视频”；不能凭页面外观、旧覆盖表或主观记忆判断。

整理者收到这三项后，必须自动完成：

1. 规范文件名并保存到 `bilibili/raw/`
2. 运行导入脚本生成 `workbench/EPxxx/`
3. 精修 `content/episodes/EPxxx.json`
4. 补齐概念 / 模型 / 人物 / 主题 / 关键词链接
5. 写入 `videoLinks`，并把人工确认链接同步到 `scripts/video-link-overrides.json`
6. 更新网页日志
7. 运行构建与 UI 回归
8. 按 Lore Commit Protocol 提交并推送 GitHub

如果用户只提供 YouTube 链接，整理者可以先自动尝试抓标题、EP 编号、字幕轨、B 站候选链接和音频；但只要 YouTube / B 站没有可下载字幕，且没有稳定可脚本调用的 ASR，就必须回到“用户提供完整字幕”的协作方式，不要假装已经有完整 transcript。

默认要求：

1. 每期节目都维护 `videoLinks`
2. 优先同时维护两条：
   - `bilibili`
   - `youtube`
3. 如果用户没有单独提供对照视频链接，必须由整理者自己主动搜索
   - 先从官方频道首页 / 投稿页直接找
   - B 站优先看 UP 主页与 `投稿`
   - YouTube 优先看频道首页与 `videos`
   - 搜索时先用节目主标题，不要一上来只搜零散关键词
   - 再用 `｜` 后面的关键词尾巴组合搜索
   - B 站和 YouTube 都要各自至少搜一轮
   - 不允许因为“用户没给链接”就直接留空
   - 也不允许在未主动搜索前就先写 `unavailable`
   - 如果 B 站默认投稿流没找到，还必须继续检查 `充电专属` 或标题里带“第二部分内容请充电收看”的相关视频
4. B 站分四种状态：
   - 普通节目：蓝色
   - 会员节目：金色会员样式
   - 暂未上架：灰色，并在 hover 时显示 `暂未上架`
   - 已下架 / 最终确认没有：灰色，并在 hover 时显示 `已下架` 或具体原因
5. YouTube 默认正常可用，当前项目按全量可用维护

批量同步命令：

```bash
npm run sync:videos
```

这个命令会自动：

1. 读取本地 B 站库存与当前清单
2. 抓取 YouTube 频道视频列表
3. 批量回填 `content/episodes/*.json` 里的 `videoLinks`
4. 自动执行 `npm run build`

也就是说，新终端里按 SOP 执行到这里时，不需要手工一个个点视频链接。

### 当自动同步找不到时怎么办

如果 `npm run sync:videos` 没有命中某一期：

1. 不要立刻把“找不到”当成最终结果
2. 必须手工去两个平台各搜一轮：
   - 先查官方频道首页 / 投稿页
   - 再搜主标题
   - 再搜主标题里的核心名词
   - 再搜 `｜` 后面的关键词尾巴
3. 手工确认后，再决定写成：
   - 真实 `url`
   - `access: "member"`
   - 新节目还没发 B 站时：`status: "unavailable"` + `note: "暂未上架"`
   - 旧节目确认消失或已被平台移除时：`status: "unavailable"` + `note: "已下架"`
4. 只有在自动同步、官方频道页检查和手工关键词搜索都失败后，才允许把旧节目标成 `已下架`
5. 新节目已知 YouTube 先发、B 站稍后更新时，不要写 `已下架`，必须写 `暂未上架`；后续用户给出 B 站链接后，要把灰色状态改成真实链接，并按实际情况补 `access: "member"`

### 视频链接判别标准

#### B 站怎么判别

B 站不是直接硬抓网页前台结果，而是优先使用本地已经保存的清单文件。

主要来源：

- `../bilibili/raw/subtitle_inventory.json`
- `../bilibili/raw/season_episodes.json`
- `scripts/video-link-overrides.json`
- B 站单条视频接口：`https://api.bilibili.com/x/web-interface/view?bvid=...`

判别顺序固定为：

1. 先读 `scripts/video-link-overrides.json`
   - 这里放人工确认过的链接
   - 只要覆盖表里有，脚本就直接信这个值
   - 后续批量同步不得覆盖人工确认链接
2. 再读本地 B 站库存：
   - `subtitle_inventory.json`
   - `season_episodes.json`
3. 用 `EPxxx` 编号优先匹配
4. 如果标题里没有明确 `EPxxx`，再用归一化标题做模糊匹配
5. 如果本地 B 站清单里确实找不到，才判成：
   - `status: "unavailable"`
   - 新节目用 `note: "暂未上架"`
   - 旧节目确认下架用 `note: "已下架"`

这一条要特别强调：

- 只要 `video-link-overrides.json`
- 或 `subtitle_inventory.json`
- 或 `season_episodes.json`

三者里任意一个能证明这一期在 B 站存在，就**禁止**把它标成灰色 `已下架`。

也就是说：

- “没在公开页看到” 不等于已下架
- “其实在会员里” 也不等于已下架
- 必须在本地证据链也找不到，才能判灰

#### B 站会员怎么判别

B 站会员态不是靠颜色猜，是靠数据或明确文本线索判断。

目前判定依据：

- 单条视频接口里的 `is_upower_exclusive === true`
- 单条视频接口 `ugc_season.sections[].episodes[]` 中，匹配当前 `bvid` 的条目 `attribute === 8`
- `season_episodes.json` 里的 `attribute === 8`
- 标题或分 P 名里明确出现：
  - `会员`
  - `会员专属`
  - `搬后会员发`
- 人工覆盖表里显式写：
  - `"access": "member"`

满足以上任一条，就按会员节目处理。

#### YouTube 怎么抓

YouTube 不是手工搜每一条，而是直接抓频道数据。

来源：

- 频道页：`https://www.youtube.com/@颖响力/videos`

抓取方式：

1. 先从频道页 HTML 里提取：
   - `ytInitialData`
   - `INNERTUBE_API_KEY`
   - `INNERTUBE_CLIENT_VERSION`
   - `VISITOR_DATA`
2. 先读首页首屏视频
3. 再用 YouTube 内部 `browse` continuation 接口继续翻页
4. 直到把频道视频列表抓全

也就是说，YouTube 当前不是靠页面可见的 30 条，而是靠 continuation 翻完整个频道。

#### YouTube 怎么匹配到 EP

优先级：

1. 标题中的 `EPxxx`
2. 描述摘要中的 `EPxxx`
3. 兼容旧写法：
   - `PE21` 这种也会识别成 `EP021`
4. 如果标题不带编号，再用归一化标题做模糊匹配

#### 手工覆盖优先

凡是你单独给过我的视频链接，都要写进：

- `scripts/video-link-overrides.json`

这是最高优先级来源。

规则：

- 手工覆盖优先于自动抓取
- 后续再跑 `npm run sync:videos` 也不能把手工链接冲掉
- 会员节目如果已经人工确认，直接在覆盖表里写 `access: "member"`
- 如果一条节目已经被人工从灰色修正为可用或会员，后续同步绝不能再回退成灰色

#### 新终端执行原则

新终端如果要补视频链接，不要自己重新发明流程。

必须按下面顺序做：

1. 先看 SOP 这段视频链接规则
2. 先看 `scripts/video-link-overrides.json` 有没有人工确认链接
3. 再运行：

```bash
npm run sync:videos
```

4. 跑完以后抽查三种样本：
   - 一条普通 B 站
   - 一条会员 B 站
   - 一条灰色已下架 B 站
   - 以及一条刚被人工修正过的节目，确认没有被重新打回灰色
5. 最后再看本地页面

最低抽查标准：

- 普通：蓝色 B 站入口
- 会员：金色 B 站入口
- 暂未上架：灰色入口，hover 显示 `暂未上架`
- 下架：灰色入口，hover 显示 `已下架`
- 人工修正过的节目：必须保持修正后的状态，不能被脚本回退

### 概念 `content/concepts/*.json`

每个概念都要能单独成立，最少要有：

- `name`
- `summary`
- `definition`
- `importance`
- `episodes`

### 思想模型 `content/models/*.json`

每个思想模型最少要有：

- `name`
- `summary`
- `definition`
- `application`
- `sourcePath`
- `episodes`

### 人物 `content/people/*.json`

人物不是简单标签，必须有最小介绍。注意：`content/people` 是源数据层，不再作为前台独立入口，站点会把人物并入关键词页。

- `summary`
- `description`
- `episodes`

要求：

- `summary` 先回答“这个人是谁”
- `description` 先补这个人的背景，再写“在这些节目里主要怎么被提及”
- 外国人物补 `englishName`
- 如果改过旧 slug，旧写法放进 `aliases`
- 不能只写标签式名字，必须有一句到一段可直接展示在网页上的简单背景介绍
- 不要让 `description` 一上来就是：
  - `在颖响力知识库里……`
  - `为什么重要……`
- 人物源数据的优先顺序是：
  1. 这个人是谁
  2. 他/她在这些节目里主要承接什么讨论线

### 主题 `content/themes/*.json`

主题用于把多个节目按议题聚合，最少要有：

- `summary`
- `description`
- `episodes`

### 关键词 `content/keywords/*.json`

关键词层用于承接品牌、人物、产品、公司、实体等更具体的检索入口，类似 GV 的公司层。人物对外统一从这里进入，不再保留独立人物页体系。

最少要有：

- `summary`
- `description`
- `aliases`
- `relatedKeywords`
- `episodes`

要求：

- `summary` 先说明这个关键词是什么类型的对象，例如人物、公司、品牌、产品、实体入口
- `description` 必须先写“它是什么 / 做什么”，再写“它为什么在颖响力知识库里重要”
- 如果这个关键词对应某个人物，优先复用 `content/people` 的信息，不要再手写一份相互冲突的人物介绍
- `relatedKeywords` 用来放：
  - 近义但不应并入 `aliases` 的相近词
  - 上位词 / 下位词
  - 同一议题簇里需要互相跳转的相关词

例如：

- 人物关键词：先写这个人是谁，再写其在专题里的位置
- 公司关键词：先写这家公司做什么，再写它在节目里代表的结构问题
