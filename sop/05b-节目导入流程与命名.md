## 原始源文件与标题标准

### 标题命名标准

- 原始节目源文件统一使用：
  - 标准字幕：`[EPxxx】 正式标题.srt`
  - 只有纯文字稿 / 聊天稿 / 手打稿：`[EPxxx】 正式标题.md`
- 标题主体只保留节目编号和正式标题，不要再把：
  - `【EP123】`
  - `｜关键词尾巴`
  - `#话题标签`
  重复塞回标题末尾
- 如果你手里只有聊天整理稿、手打文字稿、AI 转写整理稿，没有时间轴，优先保存成 `.md`，不要为了导入而伪造时间轴
- 这套知识库的标准原始字幕文件是 `.srt`；没有时间轴的原始文字稿标准文件是 `.md`
- 节目标题里如果出现 `｜` 或 `|`，后面的部分一律视为标签尾巴，不算标题正文
- 页面展示标题时，默认只显示 `｜` 前面的标题正文
- `｜` 后面的尾巴应优先进入：
  - `tags`
  - 关键词入口
  - 平台视频标题匹配辅助

例如：

- `[EP123】 伊朗为何是现代版“三国荆州”？诸葛亮庞统之争看懂大国博弈底层逻辑.srt`

### 只有文字稿时，怎么保存和导入

- 如果已经有标准字幕时间轴，直接保留原 `.srt`
- 如果只有纯文字内容、分段整理稿、聊天里发来的讲稿，直接保存成同名 `.md`
- 不要为了满足旧流程而编造 `.srt` 时间轴；只有确实需要字幕播放器或时间轴时，才把文字稿整理成顺排 `.srt`
- 对于知识库导入来说，关键是：
  - 文件名合规
  - 文本内容完整
- 导入进入知识库后，脚本会去掉时间轴，抽成纯文本 transcript 进入 `workbench/EPxxx/`

## 新终端导入 `.srt` / `.md` 的方法

### 最短命令

```bash
cd "/Users/ziqiguo/Documents/Diary/GoldenVault/md/topic/personal/sources/people/颖响力/网页"
npm run srt -- "/绝对路径/[EP123】 标题.srt"
```

只有纯文字稿时：

```bash
npm run srt -- "/绝对路径/[EP123】 标题.md"
```

如果你想强制覆盖已有节目草稿：

```bash
npm run srt -- --force "/绝对路径/[EP123】 标题.srt"
```

纯文字稿同理：

```bash
npm run srt -- --force "/绝对路径/[EP123】 标题.md"
```

如果你想把 `raw` 目录里还没进入知识库的节目一次性全部生成草稿：

```bash
npm run bootstrap:all
```

### 脚本会自动做什么

脚本：

`scripts/ingest-srt.mjs`

自动完成以下动作：

1. 检查文件名是否符合：
   `[EPxxx】 标题.srt` 或 `[EPxxx】 标题.md`
2. 如果文件不在 `bilibili/raw/`，自动复制进去
3. 把字幕或文字稿抽成纯文本 transcript
4. 在 `workbench/EPxxx/` 下生成：
   - `EPxxx.transcript.txt`
   - `EPxxx.intake.md`
5. 在 `content/episodes/` 下生成节目草稿 JSON
6. 自动执行 `npm run build`

批量脚本 `bootstrap:all` 会做同样的事，但作用对象是 `raw/` 中所有尚未生成节目 JSON 的 EP 文件。

### 脚本不会自动做什么

脚本不会自动替你完成高质量知识整理，它只负责：

- 收录
- 转写
- 搭草稿
- 重建网页

批量导入完成后，这些新节目会以 `draft` 状态进入知识库，而不是伪装成已经精修完成的条目。

你还需要手动补：

- 节目摘要
- 话题结构
- 核心观点
- 概念
- 思想模型
- 人物/主题/关键词链接

## 从聊天文字稿到网页条目的完整 SOP

适用场景：

- 你手里没有标准 `.srt`
- 只有聊天里发来的整理稿、手打稿、纯文本字幕
- 你想先把这一期塞进知识库，再继续精修

### 第一步：先把聊天内容保存成 `.md`

保存到原始字幕目录：

`/Users/ziqiguo/Documents/Diary/GoldenVault/md/topic/personal/sources/people/颖响力/bilibili/raw/`

文件名统一写成：

`[EPxxx】 正式标题.md`

例如：

`[EP123】 伊朗为何是现代版“三国荆州”？诸葛亮庞统之争看懂大国博弈底层逻辑.md`

要求：

- 这一步保存的是“原始输入”，不是最终网页文案
- 可以按语义分段保存，保留原始口播顺序
- 不要编造时间轴；导入脚本已经支持 `.md`
- 不需要提前整理成 JSON

### 第二步：运行导入脚本

在 `网页/` 目录下执行：

```bash
npm run srt -- "/绝对路径/[EP123】 正式标题.md"
```

脚本会自动生成：

- `workbench/EP123/EP123.transcript.txt`
- `workbench/EP123/EP123.intake.md`
- `content/episodes/EP123.json`
- 最新的 `dist/` 静态网页

### 第三步：看 `workbench`，不要直接对着 raw 生写

先读：

- `workbench/EP123/EP123.transcript.txt`
- `workbench/EP123/EP123.intake.md`

原因：

- `raw` 是原始存档
- `transcript` 是后续整理时真正要读的清洗文本
- `intake` 是这一期的整理清单

### 第四步：把节目草稿补成可展示条目

核心编辑文件：

`content/episodes/EP123.json`

至少先补完：

1. `summary`
2. `topic.background`
3. `topic.conflicts`
4. `topic.boundaries`
5. `topic.mechanism`
6. `topic.extensions`
7. `viewpoints`
8. `extensions`

到这一步，这一期就已经可以作为“有效网页内容”被展示，不再只是一个占位草稿。

### 第五步：继续沉淀稳定节点

如果这一期里已经出现了稳定、可复用的节点，再补到：

- `content/concepts/*.json`
- `content/models/*.json`
- `content/people/*.json`
- `content/themes/*.json`
- `content/keywords/*.json`

然后回填节目里的：

- `concepts`
- `models`
- `people`
- `themes`
- `relatedEpisodes`

### 第六步：重建并验证网页

执行：

```bash
npm run build
```

需要检查三件事：

1. 节目索引里能看到 `EP123`
2. 点进节目详情页后，不再显示“待整理”占位状态
3. 节目页里的 `summary / 话题 / 核心观点 / 延展` 都正常显示

### 第七步：什么时候算“只是导入成功”，什么时候算“网页内容有效”

只导入成功：

- raw 有源文件
- workbench 有 transcript / intake
- `content/episodes/EP123.json` 被自动创建
- 网页里能搜到这期，但点进去还是 draft 占位

网页内容有效：

- `content/episodes/EP123.json` 已补完核心字段
- 详情页显示的是结构化内容，不是占位提示
- 至少完成一轮 `npm run build` 验证

## 这轮实际采用的做法

当前高质量整理采用的是下面这套顺序：

1. 先读 transcript，抓主判断
2. 再写 `summary`
3. 再写 `topic.background / conflicts / boundaries / mechanism`
4. 再写彼此不重复的 `viewpoints`
5. 再写真正面向读者的 `extensions`
6. 再抽 `concepts / models / people / themes`
7. 最后补 `relatedEpisodes`

也就是说：

- 节目内容优先
- 节点层第二
- 页面显示第三

不要反过来做。

### 第四步：补稳定节点

如果节目里出现新的稳定内容，再补：

- 新概念：`content/concepts/*.json`
- 新模型：`content/models/*.json`
- 新人物：`content/people/*.json`
- 新主题：`content/themes/*.json`
- 新关键词：`content/keywords/*.json`

### 第五步：回填节目链接

把这些节点的 ID 回填到节目 JSON 里：

- `people`
- `themes`
- `concepts`
- `models`
- `relatedEpisodes`

### 第六步：重建和预览

```bash
npm run build
npm run serve
```

打开：

`http://127.0.0.1:4310/`

## 推荐工作顺序

每整理一集，按下面顺序走：

1. 先让节目页可读
2. 再抽概念
3. 再挂思想模型
4. 再补人物/主题/关键词
5. 最后回到网页检查跳转链路

不要一开始就试图把所有层全部写满。先保证节目条目清楚，再逐步向稳定节点沉淀。

## 入库前字数自检（build 前强制，逐项量）

新节目在 `npm run build` 和发布前，**必须逐项量字数对照下表**，超标先压再 build。字段长度的权威定义在 `sop/05a-节目字段与写作规范.md`，本表是供 build 前快速核对的速查版。

**铁律：不允许用“参考上一期”代替对照本表。** 历史节目里有超标的（如 EP152、EP153 的 summary/mechanism 都超），照抄它们等于把违规继续往下传——这是真实发生过的事故。每期只对照标准、不对照上一期。

| 字段 | 区间 | 硬上限 |
| --- | --- | --- |
| `summary` | 200–250 字 | 250 |
| `topic.mechanism` | 150–250 字 / 5–6 步 | 300 字 / 7 步 |
| mechanism 每步（箭头之间） | 20–40 字 | 40 |
| `topic.extensions` 每条 | 80–130 字 | 150 |
| `viewpoints` 条数 | 4–6 条 | 6 |
| 每条 `viewpoints[].body` | 80–150 字 | 180 |

量法（把 `EPxxx` 换成本期 id；mechanism 箭头用 ASCII `->` 或全角 `→` 都行——现存节目里 `->` 是主流，下面命令两种都数）：

```bash
python3 -c "import json;d=json.load(open('content/episodes/EPxxx.json'));t=d['topic'];m=t['mechanism'];print('summary',len(d['summary']));print('mechanism',len(m),m.count('->')+m.count('→')+1,'步');print('extensions/条',[len(x) for x in t['extensions']]);print('viewpoints',len(d['viewpoints']),'条 body',[len(v['body']) for v in d['viewpoints']])"
```

任一项超标，先回 `sop/05a` 对应字段把内容压回区间（细节下沉到 `viewpoints` / `topic`），再 build。

## 命名规则

### 节目

- 文件名固定：`EPxxx.json`

### 概念 / 模型 / 人物 / 主题 / 关键词

- 文件名统一用 slug
- `id` 与文件名保持一致
- 这个规则不只适用于人物，概念 / 模型 / 主题 / 关键词也一样遵守
- 抽象概念、机制、模型、议题主题：优先用英文语义 slug，例如 `cost-shifting`
- 中文世界的专有名词：用拼音 slug，例如中国人物、中文品牌、中文公司、中文政策名、中文事件名
- 外国专有名词：用英文常用名 slug，例如外国人物、外国公司、外国机构、外国地名、外国事件
- 不要把“中国专有名词一律翻成英文”，也不要把“外国专有名词再转写成中文拼音”
- 旧错误 slug 不继续扩散，必要时放进 `aliases`

例如：

- `cost-shifting.json`
- `authority-misinfluence.json`
- `jia-guolong.json`
- `wahaha.json`
- `donald-trump.json`
- `sanae-takaichi.json`

补充判断：

- 如果节点本质上是“抽象机制”，即使讨论中国语境，也优先用英文语义 slug
- 如果节点本质上是“具体专有名词”，就按中文专名用拼音、外国专名用英文
- 如果历史上已经有旧 slug，先保留兼容到 `aliases`，不要再新造第三种写法
